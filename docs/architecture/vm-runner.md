# VM runner

Last verified: 2026-09-23

The pods behind the `vm` Backend: **one runner per owner**, each a single-replica Deployment in the agent namespace running smolvm and the platform's **vm-runner** agent. The controller creates a runner the first time one of that owner's vm Agents reconciles, mints its token, asks cert-manager for its serving certificate, and removes it once the owner has no machines left. A runner belongs to an owner rather than to any one Agent, so no Agent can own it; the chart's runner ServiceAccount does, from the same namespace — an owner reference may not cross one — so uninstall, rollback and turning virtualization off collect the runners with it. The boundary is per owner, not per agent: one owner's machines share their runner, its disk and its credentials, so a guest that escapes its hypervisor reaches that owner's other sandboxes ([security-and-credentials](security-and-credentials.md)). Every VMM runs as the runner's own uid, so the kernel boundary is the runner and not the machine — a per-VMM uid would draw it per machine, but no VMM holding one can read the image cache the runner reaches for it, and its workload exits as soon as it starts. The runner is the one workload in the agent namespace that asks for capabilities at all. Every runner holds NET_ADMIN, for the per-machine NAT, and DAC_OVERRIDE, because its VMMs serve the image tree to their guests with the runner's own credentials and an image keeps some files from root. Only a runner that caches images on its own claim also holds CHOWN and FOWNER, which unpacking an image faithfully costs: a rootfs carries the owners and modes its files were built with, so the runner restores each owner and then sets a mode on a file it no longer owns. On a node cache the image cache service does that unpack, holding all three, and its runners only read; a staged archive is flattened inside the guest. That is the whole of what the install's SCC has to permit beyond the agent's iptables init. An agent's own container takes none of them — it is pinned to dropping all, and the controller refuses a configuration that says otherwise. Its own NetworkPolicy admits DNS, the proxy port of gateway pods carrying its owner's label, and whatever the install names in `egressCidrs`. It reaches the host's virtualization devices only as device-plugin resources, never as a privileged pod — so a cluster with no device plugin cannot host vm agents — and it stays off the ambient mesh, whose redirect would break the per-machine NAT. Its gates are not all kernel gates: a machine's egress allowlist is exactly the paired gateway's ClusterIP, but smolvm enforces it in the very process an escaped guest would own, so the runner's own NetworkPolicy is the kernel gate on where an escaped guest goes, and each gateway's ingress policy, admitting only its paired agent and its owner's runner, the gate on whose credentials it reaches. That is why an install has to state `egressCidrs` rather than inherit an open pod. Ingress is a NetworkPolicy, admitting the machine API and the published ports only from the api-server and the controller — the runner adds no source check of its own — and a token-less scrape port only from the platform's collector ([observability](observability.md#vm-runner)).

vm-runner owns a machine API — one persistent microVM per vm Agent — and takes its orders from the controller over a TLS and token call: *ensure* (the machine's whole desired shape, restart revision and power state, sent in full on every reconcile), *status* (what the machine is doing, where it is published, and why it is not ready when it is not, with the end of its console when a boot failed or went quiet ([observability](observability.md#vm-runner))) and *delete*. The runner keeps only the latest ensure for each machine and one worker converging it, one whole action at a time, so a spec that arrives mid-action — a stop sent while a machine boots — replaces any not yet acted on and is honoured when that action returns. A guest starting to answer changes nothing the cluster can watch, so the runner watches for it: a **health prober** asks each machine on its way up every half second and a steady one every ten, and a status is built from what it last heard rather than probing on the read. Each status carries a version that moves whenever the status does, and a status read may name the version it last saw and wait, up to half a minute, for it to move. The controller holds one such long poll per vm Agent whose machine is on its way up, and a change only requeues the Agent, so the ordinary reconcile is the one place readiness is written; beyond that, every vm Agent is reconciled once a minute, which is also what notices a ready guest going quiet. The runner's serving certificate is issued by cert-manager, for the runner's Service host alone, from a CA that signs runner certificates and nothing else, and the controller trusts the runner through that CA alone. It is not the gateways' MITM CA: that one signs leaves for hostnames taken from users' credential hosts, and a leaf naming a runner's host would let its key pass for that runner. Until it is issued the runner's pod cannot start and the controller cannot dial it, so the agent's reconcile waits for it as it waits for its gateway's leaf; the runner re-reads a renewed certificate in place, so a renewal reboots nothing. Each machine also gets a read-only **share** carrying the MITM CA and **platform-init**, the entrypoint that mounts the agent's home from the disk before handing off to the image's own, so persistence is the platform's to guarantee for any image ([persistence](persistence.md)). The runner's claim holds the machine disks, the bookkeeping a restart rebuilds, and the runtime's disk templates, expanded once per release rather than on every roll; the image directory is its own mount: a cache on that claim, or, read-only, a node cache or a directory of staged archives ([persistence](persistence.md)). It publishes each guest's agent port on a port of the pod, and the agent's Service selects that runner and maps the agent port onto the one its machine publishes there, so the api-server dials a vm Agent exactly like a pod. The selector reaches the runner only because the Service shares the agent namespace. A pod restart stops every machine — they are its processes — and the controller's periodic sweep brings them back.

**The runtime is one Rust workspace; the controller is its only Go peer.** The runner, the image cache service and platform-init are built together into the runner image, from that workspace alone, against one smolvm release: a single pin names it, and the crate is built from that release's source while the image installs its guest agent and disk templates, so the two are always one version. platform-init is linked statically because it runs against the agent image's libc rather than the runner's. The runner and platform-init take the guest contract — where the share is mounted, where the disk goes, where the agent's home and the platform's own state live on it — from one shared source, so the side that writes a machine's share and the side that reads it cannot disagree. The controller meets the runtime across boundaries no compiler checks: the machine API's messages and vocabulary of states and reasons, the runner's command line, and the two guest paths it also names in the agent's environment, the home and the CA file. Each is held in golden JSON documents beside the runner ([`packages/vm-runner/contract/`](../../packages/vm-runner/contract/)) that both sides' tests round-trip, so a rename on either side fails that side's own tests and neither reads the other's source. The command line has no defaults anyone relies on: the image sets the paths that are its own layout, and the controller sets everything it chose — the port range it also opens in the runner's NetworkPolicy, where it mounts the runner's state and credentials, and the budgets.

**A change to the runner pod rolls across owners, not all at once.** Because a pod restart reboots every machine of that owner, a new runner image or a controller release that renders the pod differently would otherwise reboot every vm machine in the install together, where container agents roll one at a time. The controller records a hash of the pod it rendered on each runner, leaves a runner alone while that hash is unchanged, and lets a changed one roll only while fewer than the install's roll width (one by default) are mid-roll. A runner is mid-roll from that moment until its new pod is ready and every machine that was ready before is ready again, or its agent is gone; a settle timeout bounds the wait, so a machine that never comes back does not stall everyone else. A new owner's runner is created at once, since there is nothing of theirs to protect. Rolls advance as agents reconcile and on the periodic sweep, which offers every runner its turn in name order so owners whose agents all sleep still roll. A roll still reboots each owner's machines once: nothing checkpoints them across it, and the VMM host is the same pod as the machine API it serves.

A machine may reach only its paired gateway, so the guest cannot fetch its own image: it is fetched for it, with the pull secrets a pod would list — resolving through the node's resolver rather than the cluster's, whose Service address its own egress policy drops (an install whose registry sits inside the cluster, with that range left reachable, asks for cluster resolution instead) — into a cache that unpacks each image once, evicting inside a stated budget and never freeing a tree a machine is still running from. Every machine of an image boots that one tree rather than extracting its own copy, which is what the sharing is for: an archive is unpacked again into each machine's disk, seconds of boot and a gigabyte of disk apiece for bytes that are identical. A tree is not enough on its own, because what a machine runs — the entrypoint, the environment, the directory it starts in — is named by the image and not carried by its files, so that is read with the tree and kept beside it, or read out of a staged archive; a machine whose image names none is refused rather than booted to a filesystem with nothing running in it, and so is an image the cache cannot serve, which is never booted from the registry instead. By default the cache is on the runner's own claim with the runner as its only writer, so the handful of images nearly every owner runs is fetched once per owner. Where the install shares a node directory instead, the node's **image cache service** is its only writer: runners mount it read-only and ask the service over a socket inside it, so no runner — and no guest that escapes into one — can change a tree another owner boots, and the service also preloads the install's harness images there before any runner exists to need them ([persistence](persistence.md)). What a runner may *read* there is not gated: its mount is the whole directory, so any runner on the node — and any guest that escapes into one — reads every cached tree, other owners' private images included. The per-machine access check decides only what the service resolves and fetches for a caller. The socket cannot tell one runner from another either, since every runner is root on the node, so what a caller can make the service do is bounded instead of attributed: a hold names only trees on disk, at most a thousand per call, and once holds keep the cache past half again its budget, it refuses every fetch, as a capacity problem, and logs an error for the operator. An install with no registry stages `docker save` archives in a read-only image directory instead, and the runner boots from them.

The guest is the very image the container Backend would run, booted as a VM and run as root: the VM is the isolation boundary, so the uid inside it buys nothing, and root is what bind-mounting the persisted paths, and running the container runtime, needs. Being a machine rather than a container, the guest can host what a pod cannot: a container runtime, or a whole cluster, runs inside it. Nothing supervises them — no service manager stands behind the image's init — so they start on demand and again after every stop; only what sits on a persisted path survives to be started. A machine's egress allows one destination, the paired gateway, so the controller marks the address ranges a guest might itself hold — the private, carrier-grade-NAT and link-local ones — as local to it, and a client that honors that marking reaches them directly rather than through a gateway that could never route them. What a machine keeps across a stop is its storage disk on the runner's one PVC, and nothing else ([persistence](persistence.md) owns the rule). That disk is also the only place a container runtime can keep its layers: the guest's root is an overlay, and overlayfs refuses an overlay as the upper layer of another, so a runtime whose data sits on the root never becomes ready, while under `HOME`, the disk's one path in the guest, it runs the ordinary snapshotter and a pull stays a pull rather than a copy of every layer. The base image's runtime shims put it there. Every change — size, env, MITM CA, restart revision, image or egress allowlist — is applied in place as a stop, an update of the machine's record and a start of the same machine, so the disk and port stay: smolvm reads what a machine boots and where it may send traffic from that record at every start. A new image is fetched before the old machine is touched, so a pull that fails leaves it running as it was. A stopped machine takes the change when it next starts. A machine is admitted only if its memory fits what the runner has left, counting the machines already running and those still being brought up, so an install that oversubscribes gets a refusal naming the shortfall rather than guests the kernel kills later. Each runner has its own limits, so admission is a per-owner ceiling; the controller keeps the pod's memory request, resized in place, at its running machines plus the reserve, within the install's request and the limit, so the scheduler lends out only idle headroom. Without in-place resize, or on a node that defers or refuses it, the request stays put and the controller reports it.
