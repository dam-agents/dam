# VM runner

Last verified: 2026-10-15

The pods behind the `vm` Backend: **one runner per owner**, each a single-replica Deployment in the agent namespace running smolvm and the platform's **vm-runner** agent.
A local cluster on a Mac runs one [host runner](vm-host-runner.md) outside the cluster instead.
The controller creates a runner the first time one of that owner's vm Agents reconciles, mints its token, asks cert-manager for its serving certificate, and removes it once the owner has no machines left.
A runner belongs to an owner rather than to any one Agent, so no Agent can own it; the chart's runner ServiceAccount does, from the same namespace — an owner reference may not cross one — so uninstall, rollback and turning virtualization off collect the runners with it.
The runner's claim is the one object left without an owner, like a StatefulSet's volume claims: it holds every machine disk of the owner, and one deletion of the account would otherwise take every user's disks at once.
The controller strips the account's reference from a claim that still carries one, and nothing but the [orphan sweep](#runner-lifecycle) deletes a claim.
A rollback to a controller older than this rule stamps the reference back on every claim, so the risk returns until the next upgrade strips it again.
After an uninstall, or after turning virtualization off, an operator removes the disks that are left by label: `kubectl delete pvc -n <agent namespace> -l app.kubernetes.io/component=vm-runner,app.kubernetes.io/instance=<release>`.
The boundary is per owner, not per agent: one owner's machines share their runner, its disk and its credentials, so a guest that escapes its hypervisor reaches that owner's other sandboxes ([security-and-credentials](security-and-credentials.md)).
Every VMM runs as the runner's uid, but smolvm confines each with Landlock to its machine's files, audits its syscalls, and serves the agent rootfs and image tree read-only, so no guest changes what its siblings boot.
The runner is the one long-lived workload in the agent namespace that asks for capabilities at all.
Every runner holds DAC_OVERRIDE, because its VMMs serve the image tree to their guests with the runner's own credentials and an image keeps some files from root.
Only a runner that caches images on its own claim also holds CHOWN, FOWNER and FSETID, which unpacking an image faithfully costs: a rootfs carries the owners and modes its files were built with, so the runner restores each owner and then sets a mode, setgid bits included, on a file it no longer owns.
The runner drops every other capability, cannot gain one through exec, and runs under the runtime's default seccomp profile.
Only AppArmor stays unconfined, because the runtime's default profile keeps every guest from booting.
A change to that shape changes the runner pod, so it rolls across owners like any other.
On a node cache the image cache service does that unpack, holding DAC_OVERRIDE, CHOWN, FOWNER and FSETID and nothing else, and its runners only read; a staged tree boots in place, and a staged archive is flattened inside the guest.
That, and on OpenShift the SELinux type the node cache service and the release stager ([upgrades](vm-runner-upgrades.md)) pick for themselves ([vm-image-cache](vm-image-cache.md)), is the whole of what the install's SCC has to permit beyond the agent's iptables init.
An agent's own container takes none of them — it is pinned to dropping all, and the controller refuses a configuration that says otherwise.
Its own NetworkPolicy admits the proxy and resolver ports of gateway pods carrying its owner's label and whatever the install names in `egressCidrs`, less the cloud metadata ranges, which the controller subtracts from every range that holds one.
DNS is admitted only for a runner that resolves its registry itself — one caching on its own claim — and only to the resolver it uses, named by the install: port 53 open to every address would be a two-way channel from an escaped guest to any host.
A resolver still recurses for any name, so that runner keeps one narrow channel; a runner on a node cache or staged images reaches no resolver at all.
It reaches the host's virtualization devices only as device-plugin resources, never as a privileged pod — so a cluster with no device plugin cannot host vm agents — and it stays off the ambient mesh, whose redirect would break the per-machine network.
Its gates are not all kernel gates: a machine's egress allowlist is exactly the paired gateway's ClusterIP, or, on a runner outside the cluster, one gateway port on the host's loopback in place of any allowlist — the runner refuses to run a machine with neither, since smolvm reads an empty allowlist as no filter, or one that spans every address — and a guest's DNS, which smolvm's gateway relays whatever the allowlist says, is relayed only to the paired gateway's resolver, or, on a runner outside the cluster, nowhere.
But smolvm enforces that allowlist in the very process an escaped guest would own, so the runner's own NetworkPolicy is the kernel gate on where an escaped guest goes, and each gateway's ingress policy, admitting only its paired agent and its owner's runner, the gate on whose credentials it reaches.
So a gateway is never a container of the runner pod, where an escaped guest is root.
That is why an install has to state `egressCidrs` rather than inherit an open pod.
Ingress is a NetworkPolicy, admitting the machine API and the published ports only from the api-server and the controller, and the machine API alone from the owner's own migration copy Job — the runner adds no source check of its own — and a token-less scrape port only from the platform's collector ([observability](observability.md#vm-runner)).

vm-runner owns a machine API — one persistent microVM per vm Agent — and takes its orders from the controller over a TLS and token call: *ensure* (the machine's whole desired shape, restart revision and power state, sent in full on every reconcile), *status* (what the machine is doing, where it is published, and why it is not ready when it is not, with the end of its console when a boot failed or went quiet ([observability](observability.md#vm-runner))), *pressure*, how close the runner's own memory is to its limit ([vm-memory](vm-memory.md)), *delete*, which cancels the machine's wait on an image fetch and waits a bounded time for a VMM call in flight — also one the runner gave up waiting for, and the runtime's own delete — before telling the controller to ask again, so a VMM stuck for good holds one thread however often the delete is retried, and *seed*: the home a [runtime migration](vm-runtime-migration.md) copied off an Agent's old volume, uploaded by the migration's copy Job under a [seed capability](vm-runtime-migration.md) rather than the token, accepted only for a machine that exists and is stopped, answered with a digest the sender checks against what it sent, and removed by the controller once the migration has switched the Agent's Backend; and *usage*, read-only: the claim's use, the memory admitted against the limit, the runner's CPU over the last minute, how often its limit held it back and its CPU pressure (the cgroup's pressure stall information, or that throttling where it is higher), and each machine's state, measured memory and CPU, disk size and the blocks its files take, served to the token or to a usage capability the controller derives from it for the api-server, which opens no other route.
The runner keeps only the latest ensure for each machine and one worker converging it, one whole action at a time, so a spec that arrives mid-action — a stop sent while a machine boots — replaces any not yet acted on and is honoured when that action returns.
A guest starting to answer changes nothing the cluster can watch, so the runner watches for it: a **health prober** asks each machine on its way up often, most in the first minute of its boot, and a steady one rarely, and a status is built from what it last heard rather than probing on the read.
An ensure plans from that same record while it is no older than the prober's cadence for the machine, or is about a stopped or absent machine, which only an action changes; it looks again only at an older record, one holding a runtime error, or a machine being deleted.
An ensure that reaches a runner already closing is refused, not stored.
A live VMM reads as running, not stopped, whatever its guest is doing, and a probe never pings the guest agent, so only the prober's silence restarts it: the prober itself, within a minute after an answer, ten for slow boots and repeat stalls.
Its memory stays counted meanwhile.
That a guest has answered is also read from its machine's share, where its first answer leaves a record, so a runner restarted or [handed off](vm-runner-upgrades.md) restarts a guest that answered before it and then went quiet, as its predecessor would have.
A failure stays on the status until an action succeeds or a spec arrives that needs none.
Each status carries a version that moves whenever the status does, and a status read may name the version it last saw and wait, up to half a minute, for it to move.
The controller holds one such long poll per vm Agent whose machine is on its way up, and a change only requeues the Agent, so the ordinary reconcile is the one place readiness is written; beyond that, every vm Agent is reconciled once a minute, which is also what notices a ready guest going quiet.
The runner's serving certificate is issued by cert-manager, for the runner's Service host alone, from a CA that signs runner certificates and nothing else, and the controller trusts the runner through that CA alone.
It is not the gateways' MITM CA: that one signs leaves for hostnames taken from users' credential hosts, and a leaf naming a runner's host would let its key pass for that runner.
Until it is issued the runner's pod cannot start and the controller cannot dial it, so the agent's reconcile waits for it as it waits for its gateway's leaf; the runner re-reads a renewed certificate in place, so a renewal reboots nothing.
Each machine also gets a read-only **share** carrying the MITM CA, a migration's seed until the migration completes, **platform-init**, the entrypoint that mounts the agent's home from the disk before handing off to the image's own, so persistence is the platform's to guarantee for any image, and, once the machine's guest has first answered, the record that its disk holds a home, which lets platform-init refuse a disk that has lost it ([persistence](persistence.md)); and **platform-runc**, which gives the containers the guest runs that CA ([agent-images](agent-images.md)).
The runner's claim holds the machine disks, the bookkeeping a restart rebuilds — each file of it replaced whole, never written in place, so a runner killed mid-write leaves the old one or the new — and the runtime's disk templates, expanded once per release rather than on every roll; the image directory is its own mount: a cache on that claim, or, read-only, a node cache or a directory of staged images ([persistence](persistence.md)).
It publishes each guest's agent port on a port of the pod, on an address the runner is told (every interface of a pod's own network), and the agent's Service selects that runner and maps the agent port onto the one its machine publishes there, so the api-server dials a vm Agent exactly like a pod.
The selector reaches the runner only because the Service shares the agent namespace.
A pod restart stops every machine — they are its processes — so a runner told to stop, rather than to [hand off](vm-runner-upgrades.md), first stops each running machine the way a stop does, all at once and within a window its pod's termination grace covers, rather than leaving the pod's kill to cut their power; the controller's periodic sweep brings them back.
A deleted runner pod is replaced at once, while the old one still runs that stop on the same claim, and the stop would reach the new runner's machines through the guest sockets both pods share; so a runner holds a lock on its claim for as long as its process lives, and a new one takes the claim, and only then serves, once the old process has exited.

**The runtime is one Rust workspace; the controller is its only Go peer.** The runner, the image cache service and platform-init are built together into the runner image, from that workspace alone, against one smolvm release: a single pin names it, and the crate is built from that release's source while the image installs its guest agent and disk templates, so the two are always one version.
platform-init is linked statically because it runs against the agent image's libc rather than the runner's.
The runner and platform-init take the guest contract — where the share is mounted, where the disk goes, where the agent's home and the platform's own state live on it — from one shared source, so the side that writes a machine's share and the side that reads it cannot disagree.
What outlives a runner release is versioned where it is kept: every disk is marked with the layout it is in, so a later layout change upgrades it in place at boot, a disk in a layout newer than its platform-init knows fails the boot, and a mark an unclean stop emptied counts as no mark; a stored machine spec carries its shape's version, and one of another version reads as no spec, so the machine is reshaped from the controller's next ensure.
The controller meets the runtime across boundaries no compiler checks: the machine API's messages and vocabulary of states and reasons, the runner's command line, and the two guest paths it also names in the agent's environment, the home and the CA file.
Each is held in golden JSON documents beside the runner ([`packages/vm-runner/contract/`](../../packages/vm-runner/contract/)) that both sides' tests round-trip, so a rename on either side fails that side's own tests and neither reads the other's source.
The command line has no defaults anyone relies on: the image sets the paths that are its own layout, and the controller sets everything it chose — the port range it also opens in the runner's NetworkPolicy, where it mounts the runner's state and credentials, and the budgets.

**A change to the runner pod rolls across owners, not all at once**, and a new runner image need not roll the pod at all: [upgrades](vm-runner-upgrades.md) owns both.

A machine may reach only its paired gateway, so the guest cannot fetch its own image: it is fetched for it, with the pull secrets a pod would list — resolving through the node's resolver rather than the cluster's, whose Service address its own egress policy drops (an install whose registry sits inside the cluster, with that range left reachable, asks for cluster resolution instead) — into a cache that unpacks each image once, evicting inside a stated budget and never freeing a tree a machine is still running from.
Every machine of an image boots that one tree rather than extracting its own copy: an archive is unpacked again into each machine's disk, seconds of boot and a gigabyte of disk apiece for identical bytes.
A tree is not enough on its own, because what a machine runs — the entrypoint, the environment, the directory it starts in — is named by the image and not carried by its files, so that is read with the tree and kept beside it — a staged tree carries the same record — or read out of a staged archive; a machine whose image names none is refused rather than booted to a filesystem with nothing running in it, and so is an image the cache cannot serve, which is never booted from the registry instead.
The cache has exactly one writer — the runner on its own claim, or a per-node **image cache service** where the install shares a node directory, which runners mount read-only ([vm-image-cache](vm-image-cache.md)).
An install with no registry stages images in a read-only image directory instead, and the runner boots from them: a tree with its launch record, which boots in place, or a `docker save` archive, which is flattened inside every guest on its first boot under smolvm's fixed pull window — a slow host outran that window, which is why the local install stages trees.

The guest is the very image the container Backend would run, booted as a VM and run as root: the VM is the isolation boundary, so the uid inside it buys nothing, and root is what bind-mounting the persisted paths, and running the container runtime, needs.
Being a machine rather than a container, the guest can host what a pod cannot: a container runtime, or a whole cluster, runs inside it, on a root whose mounts platform-init leaves shared as a kubelet requires.
Nothing supervises them — no service manager stands behind the image's init — so they start on demand and again after every stop; only what sits on a persisted path survives to be started.
The image's entrypoint itself is supervised.
smolvm launches a machine's workload once per boot, and platform-init, the first process of the workload's own PID namespace, cannot power the guest off, so it stays the entrypoint's parent: it reaps orphans, passes signals on, and when the entrypoint exits it says so on the machine's console, ends every process left in the namespace, and starts the entrypoint again on the same root and home, after a delay that doubles while it keeps failing.
An agent that crashed is back in seconds instead of at the runner's ten-minute unhealthy restart.
A stop signal ends the supervision instead.
platform-init's refusals to boot, each hand-off and each exit reach the console as kernel log lines, because its own log is on the disk the host never reads ([observability](observability.md#vm-runner)).
A machine's egress allows one destination, the paired gateway, so the controller marks the address ranges a guest might itself hold — the private, carrier-grade-NAT and link-local ones — as local to it, and a client that honors that marking reaches them directly rather than through a gateway that could never route them.
What a machine keeps across a stop is its storage disk on the runner's one PVC: `HOME`, and the upper layer of its root for as long as its images share a root generation ([persistence](persistence.md#per-agent-pvcs) owns the rule).
That disk is formatted once: by the runner when it creates it, with a journal and at its full size, or by smolvm on its first boot, and without a journal, when the runner has no `mkfs.ext4` or its format fails.
A start never copies smolvm's template over a disk that already holds a filesystem — not even one whose first format stopped short of resizing it to the size asked for.
A stop first sends the workload SIGTERM through the guest agent and gives it a few seconds, as a pod's container gets, then has the guest quiesce that disk, and a guest that does not confirm it did is powered off anyway, so a stop or a delete always ends the machine.
A start refuses a disk that a VMM which outlived even its kill still holds, since booting beside it would put two VMMs on one disk.
smolvm forgets a machine before it removes the machine's directory, so a delete cut short between the two leaves the disk with no record.
Every delete therefore asks the runtime, even about a machine it reads as absent, and removes a directory no record owns, and a create removes one before it makes the machine, so a machine created again under a name never boots on the home of the one deleted before it.
That disk is also the only place a container runtime can keep its layers: the guest's root is an overlay, and overlayfs refuses an overlay as the upper layer of another, so a runtime whose data sits on the root never becomes ready, while under `HOME`, the one plain path of the disk the guest keeps, it runs the ordinary snapshotter and a pull stays a pull rather than a copy of every layer.
The image's daemon configuration puts it there.
Every change — env, MITM CA, restart revision, image or egress allowlist — is applied in place as a stop, an update of the machine's record and a start of the same machine, so the disk and port stay; a new size, a larger disk included, waits for the machine's next start ([vm-memory](vm-memory.md)), so a larger storage pool reboots no agent.
A new MITM CA reaches every agent's leaf at once when the CA rotates, and every machine takes it at once too — a running one reboots onto it, since a guest still trusting only the old CA would fail every call its gateway now signs: smolvm reads what a machine boots and where it may send traffic from that record at every start.
A new image is fetched before the old machine is touched, so a pull that fails leaves it running as it was.
A stopped machine takes the change when it next starts.
A start also checks that what the record names to boot is still on the host, and resolves the image again when it is not: the record holds a path, so a tree evicted or relaid under a stopped machine would otherwise fail every start it makes.
Each runner has its own limits, so a machine is admitted against its owner's memory alone, counted by what the machines use, and the controller resizes the pod's memory request in place to match, and its memory limit to the owner's pool; each boots with part of its memory and grows once up ([vm-memory](vm-memory.md)).
It is admitted against its owner's claim too: on a claim past 90% used no machine is created or grown, and past 97% none is started or restarted ([persistence](persistence.md#per-agent-pvcs)).
Without in-place resize, or on a node that defers or refuses it, the request stays put and the controller reports it ([vm-memory](vm-memory.md)).

**A machine reaches the network without proxy settings.** In the cluster, smolvm relays every guest DNS query, whatever address it went to, to the gateway's resolver, which answers every public name with the gateway's address and never forwards or logs.
So any connection lands on the gateway, which routes TLS by SNI and HTTP by Host into the chains a CONNECT reaches, each checking egress before it dials a host of the agent's choosing ([security-and-credentials](security-and-credentials.md)).

## Runner lifecycle

**One lock per owner.** An agent's reconcile builds its owner's runner and ensures its machine under the owner's lock, and the orphan sweep takes the same lock before it looks at that runner, so the two never interleave.
The sweep removes a machine no Agent of that owner names, and removes the runner itself — its claim, and so every disk on it, with it — only when a fresh List of the owner's Agents and the controller's cache both show no vm Agent and the runner lists no machine.
The Deployment is deleted only if it is still the one the sweep checked, by UID and version, and a refusal keeps everything else for the next sweep.
A reconcile that finds any of the runner's objects still terminating from such a removal waits, and says so on the Agent, rather than building a runner on a claim that is going away.
A runner that cannot be reached is kept while its owner has any Agent at all; once the owner has none for half an hour it is removed unseen, reported as an error.

**Credentials in place.** The runner re-reads its token file every few seconds and keeps the token it holds while the file is empty or unreadable, and the controller, refused, reads the token Secret once and tries again; a refusal that stands is reported as one, apart from an unreachable runner.
Neither side rotates the token on its own, but one that changes — a Secret deleted and minted again — is honoured without restarting the pod.
A changed token also voids every seed capability minted under the old one, since their key is derived from it; the copy Job's retry carries a new one.

**Deletes and waits.** Removing a deleted Agent's machine runs from a queue that retries with backoff, off the informer's event path, so a runner that is restarting delays the cleanup and holds up nothing else; what is still left after the retries is the sweep's.
An agent whose runner is not ready is looked at again with a backoff up to a minute, and the controller watches the runner Deployments, so a runner's pod becoming ready requeues its owner's vm agents at once.
A reconcile reads the runner's Deployment and pods, and the agent's StatefulSets, from those watches and its own writes, not from the API server; a write or a resize sent from a copy that is behind fails on its resourceVersion and is decided again from a live read.
A pod is force-rolled only after a live read, and the gateway that decides whether a machine the agent no longer runs stays up is read live.
What an agent waits for is on its status: a certificate cert-manager has not issued, with cert-manager's own account; a runner pod the scheduler cannot place, under a reason of its own that the api-server reads as a failed start ([agent-lifecycle](agent-lifecycle.md#wake)), except a new pod whose state claim is still being bound, which reads as still starting for its first three minutes; a runner the kernel OOM-killed, on each agent it took down until that agent is ready again, read as still starting with the reason shown ([vm-memory](vm-memory.md)); a runner that cannot be reached, described without its in-cluster address.
A reconcile that could not ensure the machine takes the Agent's readiness down with it.
Hibernation does not wait for an unreachable runner: the gateway goes down anyway, readiness goes down, and the machine is stopped by the Agent's next reconcile.
The Agent is published hibernated only once the runner reports the machine stopped, because a wake from hibernation trusts the first health check answer ([agent-lifecycle](agent-lifecycle.md#wake)).
The runner answers a stop before the guest is signalled, quiesced and powered off, so until the machine reads stopped the Agent is not ready and reads as pausing, and its reconcile watches the machine and publishes hibernation once it stops.

## Runtime migration

A [runtime migration](vm-runtime-migration.md) moves a container Agent onto the `vm` Backend: its home is copied to the owner's runner as a seed, and the machine must prove it booted from that seed before the Agent switches.
