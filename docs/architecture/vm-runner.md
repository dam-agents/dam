# VM runner

Last verified: 2026-09-23

The pods behind the `vm` Backend: **one runner per owner**, each a single-replica Deployment in the agent namespace running smolvm and the platform's **vm-runner** agent. The controller creates a runner the first time one of that owner's vm Agents reconciles, mints its credentials, and removes it once the owner has no machines left. A runner belongs to an owner rather than to any one Agent, so no Agent can own it; the chart's runner ServiceAccount does, from the same namespace — an owner reference may not cross one — so uninstall, rollback and turning virtualization off collect the runners with it. The boundary is per owner, not per agent: one owner's machines share their runner, its disk and its credentials, so a guest that escapes its hypervisor reaches that owner's other sandboxes ([security-and-credentials](security-and-credentials.md)). Every VMM runs as the runner's own uid, so the kernel boundary is the runner and not the machine — a per-VMM uid would draw it per machine, but no VMM holding one can read the image cache the runner reaches for it, and its workload exits as soon as it starts. The runner is the one workload in the agent namespace that asks for capabilities at all, and its set — NET_ADMIN, CHOWN, FOWNER, DAC_OVERRIDE — is the whole of what the install's SCC has to permit beyond the agent's iptables init. All three beyond NET_ADMIN are what unpacking an image faithfully costs: a rootfs carries the owners and modes its files were built with, so the runner restores both, and keeps writing into directories that are read-only or no longer its own — which permission bits forbid even to root. Withdrawing any of them leaves an uncached image unusable. An agent's own container takes none of them — it is pinned to dropping all, and the controller refuses a configuration that says otherwise. It does not stop there: the runner's own NetworkPolicy admits gateway pods as a class, because they carry no owner label, along with DNS and whatever the install names in `egressCidrs`. It reaches the host's virtualization devices only as device-plugin resources, never as a privileged pod — so a cluster with no device plugin cannot host vm agents — and it stays off the ambient mesh, whose redirect would break the per-machine NAT. Its gates are not all kernel gates: a machine's egress allowlist is exactly the paired gateway's ClusterIP, but smolvm enforces it in the very process an escaped guest would own, so the runner's own NetworkPolicy is the only gate behind it — which is why an install has to state `egressCidrs` rather than inherit an open pod. Ingress is a NetworkPolicy, admitting the machine API and the published ports only from the api-server and the controller, and a token-less scrape port only from the platform's collector ([observability](observability.md#vm-runner)).

vm-runner owns a machine API — one persistent microVM per vm Agent — and takes its orders from the controller over a TLS and token call: *ensure* (the machine's shape, restart revision and desired power state), *status* (what the machine is doing, where it is published, and why it is not ready when it is not, with the end of its console when a boot failed or went quiet ([observability](observability.md#vm-runner))) and *delete*. Each machine also gets a read-only **share** carrying the MITM CA and **platform-init**, the entrypoint that mounts the agent's home from the disk before handing off to the image's own, so persistence is the platform's to guarantee for any image ([persistence](persistence.md)). The runner's claim holds the machine disks and the bookkeeping a restart rebuilds; the image cache is its own mount, on that claim or on a node directory ([persistence](persistence.md)). It publishes each guest's agent port on a port of the pod, and the agent's Service selects that runner and maps the agent port onto the one its machine publishes there, so the api-server dials a vm Agent exactly like a pod. The selector reaches the runner only because the Service shares the agent namespace. A pod restart stops every machine — they are its processes — and the controller's periodic sweep brings them back.

**A change to the runner pod rolls across owners, not all at once.** Because a pod restart reboots every machine of that owner, a new runner image or a controller release that renders the pod differently would otherwise reboot every vm machine in the install together, where container agents roll one at a time. The controller records a hash of the pod it rendered on each runner, leaves a runner alone while that hash is unchanged, and lets a changed one roll only while fewer than the install's roll width (one by default) are mid-roll. A runner is mid-roll from that moment until its new pod is ready and every machine that was ready before is ready again, or its agent is gone; a settle timeout bounds the wait, so a machine that never comes back does not stall everyone else. A new owner's runner is created at once, since there is nothing of theirs to protect. Rolls advance as agents reconcile and on the periodic sweep, which offers every runner its turn in name order so owners whose agents all sleep still roll. An install can also name a **canary** runner image for a subset of owners — listed by owner, or a percentage picked by a stable hash of the owner so the same owners are picked every time and a higher percentage only adds more — and that image rolls in through the same gate. A roll still reboots each owner's machines once: nothing checkpoints them across it, and the VMM host is the same pod as the machine API it serves.

A machine may reach only its paired gateway, so the guest cannot fetch its own image: the runner fetches it — resolving through the node's resolver rather than the cluster's, whose Service address its own egress policy drops (an install whose registry sits inside the cluster, with that range left reachable, asks for cluster resolution instead) — onto its cache, where it unpacks each image once, evicting inside a stated budget and never freeing a tree a machine is still running from. Every machine of an image boots that one tree rather than extracting its own copy, which is what the sharing is for: an archive is unpacked again into each machine's disk, seconds of boot and a gigabyte of disk apiece for bytes that are identical. A tree is not enough on its own, because what a machine runs — the entrypoint, the environment, the directory it starts in — is named by the image and not carried by its files, so that is read with the tree and kept beside it, read out of the archive a machine falls back to, or fetched from the registry on its own; a machine whose image names none is refused rather than booted to a filesystem with nothing running in it. The handful of images nearly every owner runs is therefore fetched once per cache — once per owner by default, or once per node where the install shares a directory. A node directory also has a **cache service**: no runner exists before an agent needs one, so it is this that preloads the install's harness images and pins them against an eviction that takes what nobody runs first ([persistence](persistence.md)).

The guest is the very image the container Backend would run, booted as a VM and run as root: the VM is the isolation boundary, so the uid inside it buys nothing, and root is what bind-mounting the persisted paths, and running the container runtime, needs. Being a machine rather than a container, the guest can host what a pod cannot: a container runtime, or a whole cluster, runs inside it. Nothing supervises them — no service manager stands behind the image's init — so they start on demand and again after every stop; only what sits on a persisted path survives to be started. A machine's egress allows one destination, the paired gateway, so the controller marks the address ranges a guest might itself hold — the private, carrier-grade-NAT and link-local ones — as local to it, and a client that honors that marking reaches them directly rather than through a gateway that could never route them. What a machine keeps across a stop is its storage disk on the runner's one PVC, and nothing else ([persistence](persistence.md) owns the rule). That disk is also the only place a container runtime can keep its layers: the guest's root is an overlay, and overlayfs refuses an overlay as the upper layer of another, so a runtime whose data sits on the root never becomes ready, while on the storage disk it runs the ordinary snapshotter and a pull stays a pull rather than a copy of every layer. A change of size, env, MITM CA or restart revision is applied in place as a stop, update and start of the same machine, so the disk stays; the image is fixed at create, so a template upgrade reaches new machines only. A machine is admitted only if its memory fits what the runner has left, counting the machines already running, so an install that oversubscribes gets a refusal naming the shortfall rather than guests the kernel kills later. Each runner has its own limits, so admission is a per-owner ceiling; the controller keeps the pod's memory request, resized in place, at its running machines plus the reserve, within the install's request and the limit, so the scheduler lends out only idle headroom. Without in-place resize, or on a node that defers or refuses it, the request stays put and the controller reports it.
