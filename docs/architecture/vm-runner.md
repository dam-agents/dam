# VM runner

Last verified: 2026-09-28

The pods behind the `vm` Backend: **one runner per owner**, each a single-replica Deployment in the agent namespace running smolvm and the platform's **vm-runner** agent. The controller creates a runner the first time one of that owner's vm Agents reconciles, mints its token, asks cert-manager for its serving certificate, and removes it once the owner has no machines left. A runner belongs to an owner rather than to any one Agent, so no Agent can own it; the chart's runner ServiceAccount does, from the same namespace — an owner reference may not cross one — so uninstall, rollback and turning virtualization off collect the runners with it. The boundary is per owner, not per agent: one owner's machines share their runner, its disk and its credentials, so a guest that escapes its hypervisor reaches that owner's other sandboxes ([security-and-credentials](security-and-credentials.md)). Every VMM runs as the runner's own uid, so the kernel boundary is the runner and not the machine — a per-VMM uid would draw it per machine, but no VMM holding one can read the image cache the runner reaches for it, and its workload exits as soon as it starts. The runner is the one long-lived workload in the agent namespace that asks for capabilities at all. Every runner holds NET_ADMIN, for the per-machine NAT, and DAC_OVERRIDE, because its VMMs serve the image tree to their guests with the runner's own credentials and an image keeps some files from root. Only a runner that caches images on its own claim also holds CHOWN, FOWNER and FSETID, which unpacking an image faithfully costs: a rootfs carries the owners and modes its files were built with, so the runner restores each owner and then sets a mode, setgid bits included, on a file it no longer owns. The runner drops every other capability, cannot gain one through exec, and runs under the runtime's default seccomp profile; only AppArmor stays unconfined, because the runtime's default profile keeps every guest from booting. A change to that shape changes the runner pod, so it rolls across owners like any other. On a node cache the image cache service does that unpack, holding DAC_OVERRIDE, CHOWN, FOWNER and FSETID and nothing else, and its runners only read; a staged tree boots in place, and a staged archive is flattened inside the guest. That, and on OpenShift the SELinux type the node cache service picks for itself ([vm-image-cache](vm-image-cache.md)), is the whole of what the install's SCC has to permit beyond the agent's iptables init. An agent's own container takes none of them — it is pinned to dropping all, and the controller refuses a configuration that says otherwise. Its own NetworkPolicy admits the proxy port of gateway pods carrying its owner's label and whatever the install names in `egressCidrs`, less the cloud metadata ranges, which the controller subtracts from every range that holds one. DNS is admitted only for a runner that resolves its registry itself — one caching on its own claim — and only to the resolver it uses, named by the install: port 53 open to every address would be a two-way channel from an escaped guest to any host. A resolver still recurses for any name, so that runner keeps one narrow channel; a runner on a node cache or staged images reaches no resolver at all. It reaches the host's virtualization devices only as device-plugin resources, never as a privileged pod — so a cluster with no device plugin cannot host vm agents — and it stays off the ambient mesh, whose redirect would break the per-machine NAT. Its gates are not all kernel gates: a machine's egress allowlist is exactly the paired gateway's ClusterIP — the runner refuses to run a machine whose allowlist is empty, which smolvm reads as no filter, or spans every address — and a guest's DNS, which smolvm's gateway relays whatever the allowlist says, is relayed to a resolver that does not exist, since nothing in a guest resolves names: its proxy is an address, and the gateway pod resolves what it asks for. But smolvm enforces that allowlist in the very process an escaped guest would own, so the runner's own NetworkPolicy is the kernel gate on where an escaped guest goes, and each gateway's ingress policy, admitting only its paired agent and its owner's runner, the gate on whose credentials it reaches. That is why an install has to state `egressCidrs` rather than inherit an open pod. Ingress is a NetworkPolicy, admitting the machine API and the published ports only from the api-server and the controller, and the machine API alone from the owner's own migration copy Job — the runner adds no source check of its own — and a token-less scrape port only from the platform's collector ([observability](observability.md#vm-runner)).

vm-runner owns a machine API — one persistent microVM per vm Agent — and takes its orders from the controller over a TLS and token call: *ensure* (the machine's whole desired shape, restart revision and power state, sent in full on every reconcile), *status* (what the machine is doing, where it is published, and why it is not ready when it is not, with the end of its console when a boot failed or went quiet ([observability](observability.md#vm-runner))), *delete*, which cancels the machine's wait on an image fetch and waits a bounded time for a VMM call in flight, answering 503 for the controller to ask again rather than holding its request, and *seed*: the home a [runtime migration](#runtime-migration) copied off an Agent's old volume, uploaded by the migration's copy Job under a [seed capability](#runtime-migration) rather than the token, accepted only for a machine that exists and is stopped, answered with a digest the sender checks against what it sent, and removed by the controller once the migration has switched the Agent's Backend. The runner keeps only the latest ensure for each machine and one worker converging it, one whole action at a time, so a spec that arrives mid-action — a stop sent while a machine boots — replaces any not yet acted on and is honoured when that action returns. A guest starting to answer changes nothing the cluster can watch, so the runner watches for it: a **health prober** asks each machine on its way up every half second and a steady one every ten, and a status is built from what it last heard rather than probing on the read. An ensure that reaches a runner already closing is answered 503 and not stored. A live VMM whose guest agent is slow to answer smolvm's ping reads as running, not stopped: a busy guest looks the same as a dead agent there, so only the prober's silence past the unhealthy grace restarts it, and it keeps its memory counted meanwhile. A failure stays on the status until an action succeeds or a spec arrives that needs none. Each status carries a version that moves whenever the status does, and a status read may name the version it last saw and wait, up to half a minute, for it to move. The controller holds one such long poll per vm Agent whose machine is on its way up, and a change only requeues the Agent, so the ordinary reconcile is the one place readiness is written; beyond that, every vm Agent is reconciled once a minute, which is also what notices a ready guest going quiet. The runner's serving certificate is issued by cert-manager, for the runner's Service host alone, from a CA that signs runner certificates and nothing else, and the controller trusts the runner through that CA alone. It is not the gateways' MITM CA: that one signs leaves for hostnames taken from users' credential hosts, and a leaf naming a runner's host would let its key pass for that runner. Until it is issued the runner's pod cannot start and the controller cannot dial it, so the agent's reconcile waits for it as it waits for its gateway's leaf; the runner re-reads a renewed certificate in place, so a renewal reboots nothing. Each machine also gets a read-only **share** carrying the MITM CA, a migrated machine's links plan, a migration's seed until the migration completes, **platform-init**, the entrypoint that mounts the agent's home from the disk before handing off to the image's own, so persistence is the platform's to guarantee for any image, and, once the machine's guest has first answered, the record that its disk holds a home, which lets platform-init refuse a disk that has lost it ([persistence](persistence.md)). The runner's claim holds the machine disks, the bookkeeping a restart rebuilds — each file of it replaced whole, never written in place, so a runner killed mid-write leaves the old one or the new — and the runtime's disk templates, expanded once per release rather than on every roll; the image directory is its own mount: a cache on that claim, or, read-only, a node cache or a directory of staged images ([persistence](persistence.md)). It publishes each guest's agent port on a port of the pod, and the agent's Service selects that runner and maps the agent port onto the one its machine publishes there, so the api-server dials a vm Agent exactly like a pod. The selector reaches the runner only because the Service shares the agent namespace. A pod restart stops every machine — they are its processes — so a runner told to stop first stops each running machine the way a stop does, all at once and within a window its pod's termination grace covers, rather than leaving the pod's kill to cut their power; the controller's periodic sweep brings them back.

**The runtime is one Rust workspace; the controller is its only Go peer.** The runner, the image cache service and platform-init are built together into the runner image, from that workspace alone, against one smolvm release: a single pin names it, and the crate is built from that release's source while the image installs its guest agent and disk templates, so the two are always one version. platform-init is linked statically because it runs against the agent image's libc rather than the runner's. The runner and platform-init take the guest contract — where the share is mounted, where the disk goes, where the agent's home and the platform's own state live on it — from one shared source, so the side that writes a machine's share and the side that reads it cannot disagree. The controller meets the runtime across boundaries no compiler checks: the machine API's messages and vocabulary of states and reasons, the runner's command line, and the two guest paths it also names in the agent's environment, the home and the CA file. Each is held in golden JSON documents beside the runner ([`packages/vm-runner/contract/`](../../packages/vm-runner/contract/)) that both sides' tests round-trip, so a rename on either side fails that side's own tests and neither reads the other's source. The command line has no defaults anyone relies on: the image sets the paths that are its own layout, and the controller sets everything it chose — the port range it also opens in the runner's NetworkPolicy, where it mounts the runner's state and credentials, and the budgets.

**A change to the runner pod rolls across owners, not all at once.** Because a pod restart reboots every machine of that owner, a new runner image or a controller release that renders the pod differently would otherwise reboot every vm machine in the install together, where container agents roll one at a time. The controller records a hash of the pod it rendered on each runner, leaves a runner alone while that hash is unchanged, and lets a changed one roll only while fewer than the install's roll width (one by default) are mid-roll. A runner is mid-roll from that moment until its new pod is ready and every machine that was ready before is ready again, or its agent is gone; a settle timeout bounds the wait for machines, so one that never comes back does not stall everyone else. A new pod that is still not ready at the timeout is a broken runner release, not a slow machine: that roll keeps its place, so the release goes no further, and is marked stalled and reported as an error until its pod becomes ready or the pod changes again. A runner whose pod is unchanged is not rolled, but labels or owner references that drifted on it are put back without touching the pod. A new owner's runner is created at once, since there is nothing of theirs to protect. Rolls advance as agents reconcile and on the periodic sweep, which offers every runner its turn in name order so owners whose agents all sleep still roll; which runners are mid-roll is read once every few seconds rather than on every turn, and a roll the controller starts counts at once. The sweep only ever updates a runner that exists — creating one is an agent's reconcile's alone. A roll still reboots each owner's machines once: nothing checkpoints them across it, and the VMM host is the same pod as the machine API it serves.

A machine may reach only its paired gateway, so the guest cannot fetch its own image: it is fetched for it, with the pull secrets a pod would list — resolving through the node's resolver rather than the cluster's, whose Service address its own egress policy drops (an install whose registry sits inside the cluster, with that range left reachable, asks for cluster resolution instead) — into a cache that unpacks each image once, evicting inside a stated budget and never freeing a tree a machine is still running from. Every machine of an image boots that one tree rather than extracting its own copy, which is what the sharing is for: an archive is unpacked again into each machine's disk, seconds of boot and a gigabyte of disk apiece for bytes that are identical. A tree is not enough on its own, because what a machine runs — the entrypoint, the environment, the directory it starts in — is named by the image and not carried by its files, so that is read with the tree and kept beside it — a staged tree carries the same record — or read out of a staged archive; a machine whose image names none is refused rather than booted to a filesystem with nothing running in it, and so is an image the cache cannot serve, which is never booted from the registry instead. The cache has exactly one writer — the runner on its own claim, or a per-node **image cache service** where the install shares a node directory, which runners mount read-only ([vm-image-cache](vm-image-cache.md)). An install with no registry stages images in a read-only image directory instead, and the runner boots from them: a tree with its launch record, which boots in place, or a `docker save` archive, which is flattened inside every guest on its first boot under smolvm's fixed pull window — a slow host outran that window, which is why the local install stages trees.

The guest is the very image the container Backend would run, booted as a VM and run as root: the VM is the isolation boundary, so the uid inside it buys nothing, and root is what bind-mounting the persisted paths, and running the container runtime, needs. Being a machine rather than a container, the guest can host what a pod cannot: a container runtime, or a whole cluster, runs inside it, on a root whose mounts platform-init leaves shared as a kubelet requires. Nothing supervises them — no service manager stands behind the image's init — so they start on demand and again after every stop; only what sits on a persisted path survives to be started. The image's entrypoint itself is supervised. smolvm launches a machine's workload once per boot, and platform-init, the first process of the workload's own PID namespace, cannot power the guest off, so it stays the entrypoint's parent: it reaps orphans, passes signals on, and when the entrypoint exits it says so on the machine's console, ends every process left in the namespace, and starts the entrypoint again on the same root and home, after a delay that doubles while it keeps failing. An agent that crashed is back in seconds instead of at the runner's ten-minute unhealthy restart. A stop signal ends the supervision instead. platform-init's refusals to boot, each hand-off and each exit reach the console as kernel log lines, because its own log is on the disk the host never reads ([observability](observability.md#vm-runner)). A machine's egress allows one destination, the paired gateway, so the controller marks the address ranges a guest might itself hold — the private, carrier-grade-NAT and link-local ones — as local to it, and a client that honors that marking reaches them directly rather than through a gateway that could never route them. What a machine keeps across a stop is its storage disk on the runner's one PVC, and nothing else ([persistence](persistence.md) owns the rule). A stop first sends the workload SIGTERM through the guest agent and gives it a few seconds, as a pod's container gets, then has the guest quiesce that disk, and a guest that does not confirm it did is powered off anyway, so a stop or a delete always ends the machine. A start refuses a disk that a VMM which outlived even its kill still holds, since booting beside it would put two VMMs on one disk. That disk is also the only place a container runtime can keep its layers: the guest's root is an overlay, and overlayfs refuses an overlay as the upper layer of another, so a runtime whose data sits on the root never becomes ready, while under `HOME`, the disk's one path in the guest, it runs the ordinary snapshotter and a pull stays a pull rather than a copy of every layer. The image's daemon configuration puts it there. Every change — size, env, MITM CA, restart revision, image or egress allowlist — is applied in place as a stop, an update of the machine's record and a start of the same machine, so the disk and port stay. A new MITM CA reaches every agent's leaf at once when the CA rotates, and every machine takes it at once too — a running one reboots onto it, since a guest still trusting only the old CA would fail every call its gateway now signs: smolvm reads what a machine boots and where it may send traffic from that record at every start. A new image is fetched before the old machine is touched, so a pull that fails leaves it running as it was. A stopped machine takes the change when it next starts. A start also checks that what the record names to boot is still on the host, and resolves the image again when it is not: the record holds a path, so a tree evicted or relaid under a stopped machine would otherwise fail every start it makes. A machine is admitted only if its memory fits what the runner has left, counting the machines already running and each one an action is still bringing up — at the larger of its old and new size, and even with a stop waiting behind the boot — so an install that oversubscribes gets a refusal naming the shortfall rather than guests the kernel kills later. Each runner has its own limits, so admission is a per-owner ceiling; the controller keeps the pod's memory request, resized in place, at its running machines plus the reserve, within the install's request and the limit, so the scheduler lends out only idle headroom. Without in-place resize, or on a node that defers or refuses it, the request stays put and the controller reports it.

## Runner lifecycle

**One lock per owner.** An agent's reconcile builds its owner's runner and ensures its machine under the owner's lock, and the orphan sweep takes the same lock before it looks at that runner, so the two never interleave. The sweep removes a machine no Agent of that owner names, and removes the runner itself — its claim, and so every disk on it, with it — only when a fresh List of the owner's Agents and the controller's cache both show no vm Agent and the runner lists no machine. The Deployment is deleted only if it is still the one the sweep checked, by UID and version, and a refusal keeps everything else for the next sweep. A reconcile that finds any of the runner's objects still terminating from such a removal waits, and says so on the Agent, rather than building a runner on a claim that is going away. A runner that cannot be reached is kept while its owner has any Agent at all; once the owner has none for half an hour it is removed unseen, reported as an error.

**Credentials in place.** The runner re-reads its token file every few seconds and keeps the token it holds while the file is empty or unreadable, and the controller, refused, reads the token Secret once and tries again; a refusal that stands is reported as one, apart from an unreachable runner. Neither side rotates the token on its own, but one that changes — a Secret deleted and minted again — is honoured without restarting the pod. A changed token also voids every seed capability minted under the old one, since their key is derived from it; the copy Job's retry carries a new one.

**Deletes and waits.** Removing a deleted Agent's machine runs from a queue that retries with backoff, off the informer's event path, so a runner that is restarting delays the cleanup and holds up nothing else; what is still left after the retries is the sweep's. An agent whose runner is not ready is looked at again with a backoff up to a minute, and the controller watches the runner Deployments, so a runner's pod becoming ready requeues its owner's vm agents at once. What an agent waits for is on its status: a certificate cert-manager has not issued, with cert-manager's own account; a runner pod the scheduler cannot place, under a reason of its own that the api-server reads as a failed start ([agent-lifecycle](agent-lifecycle.md#wake)); a runner that cannot be reached, described without its in-cluster address. A reconcile that could not ensure the machine takes the Agent's readiness down with it. Hibernation does not wait for an unreachable runner: the gateway goes down anyway and the machine is stopped by the Agent's next reconcile.

## Runtime migration

A **runtime migration** moves one container Agent onto the `vm` Backend at the user's request, and can be undone until the Agent's machine has booted from the copy; the UI offers it only to users who opted into the new runtime. A machine keeps only `HOME` ([persistence](persistence.md#per-agent-pvcs)), so each other persisted path moves into it: one under `HOME` keeps its place, and one outside moves to the same path below `HOME/.persisted` — `/data` to `/home/agent/.persisted/data` — and platform-init puts `/data` back on every boot, before the image's entrypoint, since the root is fresh each time, so the agent's software finds its data where it was. The plan is the Agent's own: each moved mount keeps the path it came from, the controller sends that list with every ensure — from the target shape while the migration runs beside the container, and from the spec once the switch has written it there — and the runner writes it into the machine's read-only share, so it outlives the migration and the agent cannot change it. An absent path, an empty directory or a dangling link becomes a symlink into `HOME`; a directory the image ships content in has the home's copy mounted over it, hiding the image's as the container's volume did; a path inside another moved path is reached through that one. No symlink is followed on the way, whether the agent planted it in its home or the image ships it, and nothing needs a shell. A path that cannot be put back fails the boot, with its reason on the console and so on the Agent, rather than letting the agent write where a stop discards it. Unlike a mount, the symlink is visible: `ls -l /data` shows where the data lives, and a tool that resolves links sees the path under `HOME`. The api-server plans from the mounts the controller renders — the Agent's own, or the install's template defaults when it names none — and refuses a path whose link would break the guest, naming why — any mount path that is not plain, checked first even under `HOME`, the root, `HOME` or anything above it, a path the platform lays out in the guest or anything above or inside one, or one already below `.persisted` — an Agent that does not persist `HOME`, which leaves nothing to carry, an Agent already being moved or still clearing up an earlier move, and one mid-way through a storage migration; the UI offers the move from that same refusal. Otherwise it writes a request and no spec: the **target** shape — the rendered mounts with the moved ones rewritten, each naming the path it came from, and the disk sized for all the volumes together — a **snapshot** of every field the switch will change (Backend, mounts, storage size, runtime class, node selector) with the rendered mounts beside it, none naming where it came from, and where each path went. That write, and every later one — an abort, a retry, the switch — is conditioned on the version of the Agent it was decided from, so a change in between — a storage migration starting, a second request, the controller's status — fails it as a conflict, decided again from a fresh read and reported to retry if it keeps losing. The container spec stays the Agent's spec until the machine has proven the copy, so the api-server stays the only spec writer and the switch is its write, not the controller's. The rest is the controller's, and every step is derived from cluster state and from the migration's status condition — its phase, its reason and the copy attempts — so a restart resumes it. It first makes the owner's runner and the machine, stopped, in the target shape, while the container keeps running and keeps its Service: that **preflight** proves the runner schedules, the image is fetched and unpacked and the disk is made before the Agent loses anything, and whatever it waits on is its reason. Memory is admitted only when a machine starts, so a runner too small for it shows at the boot, still before the point of no return. Only then does it scale the container's StatefulSet to zero — keeping it, and its claims, for an abort, and the storage migration leaves those claims alone while a runtime migration runs — and record which volume held `HOME` and each moved path; once the pod is gone it runs a copy Job — the runner image's own archive writer, reading the volumes read-only — that streams them as one tree to the owner's runner, each other volume grafted in where its path now lives and hiding what the home volume held beneath its old mount, so the seed and its restore stay a single home; and only then lets the machine boot, so platform-init seeds the fresh disk from the copy instead of from the image. The machine boots once even for an Agent that was asleep, because only a guest that answered proves the copy, and while it boots the gateway serves the machine, admitting the owner's runner, and the container stays down. A guest that answers with its home from the copy's seed, as the next paragraph says, makes the migration **verified**, the point of no return; the api-server, which polls for verified Agents, then switches the Backend to the target shape and withdraws the request in one write, and only after that does the controller remove the StatefulSet, the headless Service and the seed and retain the old volumes. A copy that fails is reported with the copy Job's own error and retried; after three attempts, or once the migration has run for six hours, it is **failed**, with the reason on the Agent. A failed migration keeps a container it had stopped stopped and one it never stopped running, until the user retries or aborts. A **retry** starts over from the preflight with a fresh machine, since a boot that failed may have seeded part of its disk. An **abort** is valid in every phase before verified: the api-server withdraws the request and writes the snapshot's fields back, and the controller deletes the copy Job and the machine with its seed and removes the condition; the old volumes never lost their labels, so the container resumes on them as they were. Both writes carry the version they were decided from — the api-server's abort against the controller's status, the controller's verified mark against the request — so exactly one of an abort and a verified boot wins. The copy Job waits for the runner to accept its connection before it uploads, because a policy engine admits a new pod to the runner's ingress rule only after the pod exists.

**The copy Job holds a seed capability, never the runner's token.** The Job parses what an agent wrote, and the token drives every route for every machine of the owner, so the controller mints the Job a capability instead: an HMAC over the machine, the seed scope, a random nonce and an expiry, keyed with a key derived from the runner's token under a fixed label, so the runner checks it with no second secret to distribute and the Job cannot work the token back out of it. It is fresh for every Job, expires shortly after the Job's active deadline, and sits in a Secret that only that Job mounts and that is deleted with it, and whenever the migration is aborted, retried or fails. The runner accepts it on the seed upload of the machine it names and nowhere else, and only while the controller's latest spec for that machine marks it as migrating — the controller sets the mark from the preflight until the copy is in and drops it before the first boot or when the migration fails, and a retry's fresh machine takes it again — no guest has yet answered from the machine's disk, and the capability is unspent. A seed not yet booted from may be replaced, because an attempt can store its seed and still fail with its answer lost; each Job makes one attempt, so the retry is a new Job with a fresh capability. A capability is spent before its seed is stored, and what was spent is kept on the runner's claim beside the machine, so a restart does not forget it. The token still opens the seed upload and every other route; the controller itself never seeds. Each stored seed goes on the runner's security log with its machine, size, digest and what let it in, and each refused capability with the reason, naming a capability only by a fingerprint the controller also logs when it mints one. A runner not yet rolled onto a release that knows capabilities refuses them, so a migration on it retries until its runner rolls. Both sides hold the derivation to a shared contract document ([`packages/vm-runner/contract/`](../../packages/vm-runner/contract/)).

**The boot is held to the copy.** A guest that answers proves only that it booted, and a seed can go missing between the copy and the boot — a runner claim lost or recreated, a node that crashed before the upload was durable, an operator — after which platform-init would seed the image's home and the migration would look done. So the seed is a contract from end to end. The copy Job reports the seed the runner stored, its size and digest, once the runner's answer matched what was sent; the controller records it on the Agent and sends it with the machine's desired shape for as long as the migration boots, and a boot with no seed recorded is held down. The runner starts that machine only while its share holds exactly that seed, judged by the digest its upload was answered with, and otherwise refuses under a reason of its own; it also writes the expectation into the share, where the guest reads it and cannot change it. platform-init then restores the home from that seed, hashing it as it unpacks, or fails the boot — it never falls back to the image — and records on the disk which seed it used, so a reboot before the migration ends mounts that home again and refuses any other. When the guest first answers, the runner records the expected seed as the one the home came from and reports it in the machine's status: platform-init let the image start only on a home from that seed, so the answer is the proof, and nothing is read off a disk the guest has had root on. A change in the expectation alone restarts no machine. The controller marks the migration verified only when the machine is ready and reports the seed it expects. A seed the runner does not hold, a home from anything else, or a copy that did not say which seed it stored sends the migration back to copying, with the reason on the Agent: the machine is deleted, so the new copy lands on a fresh disk, and the old volumes, which keep their labels until the switch, are copied again, as one more copy attempt. A runner that reports no seed reads as a home from elsewhere, so its migrations are copied again until the owner's runner rolls onto a release that does.

**The copy Job is confined, pinned and throttled.** It runs under the runtime's default seccomp profile with no escalation and a read-only root; all-shared volumes are read as the agent's uid, a set with any block volume as root holding DAC_READ_SEARCH alone. Its own NetworkPolicy reaches only the owner's runner, pinned by address with no DNS, and copies are capped per install and per owner. An Agent with no volume skips the copy and boots from the image, still through the verified boot and the switch. What holds a migration up is said as [observability](observability.md#runtime-migration) describes.

**What the user is told.** Before anything is written, the api-server answers a read-only **plan** for the move, read off the very request a migrate would record and the same refusal it checks, so the plan and the request cannot disagree: each persisted path and where it will live, the paths that cannot move and why, the disk's new size, whether a sleeping Agent will be started to finish the move — which counts against its owner's [budget](budgets.md) while it runs — and the retention window below, read from the same chart value the controller uses. The confirm dialog shows that plan, and says the move can be aborted until the Agent has started on the new runtime. An Agent the api-server would refuse keeps a disabled Migrate whose card, opened by hover or tap, lists the refusal reasons in the words the request refuses with. From the container's stop until the machine has booted from the copy the Agent reads as **migrating**, ahead of every state but an error, and so does one whose migration failed after the stop, since it stays stopped until retried or aborted; through the preflight, an abort and a verified boot it reads as whichever side is starting or running. A wake for a migrating Agent is refused at once rather than waited out, so a chat reads "moving to the new runtime", a [channel](channel-turns.md) message is answered "try again in a few minutes" — or, after a failure, that the move failed and waits on its owner — instead of timing out, and a [schedule](schedules.md#fire) fire is held.

**The old volumes are retained.** Once the Backend has switched, each volume the copy was read from is kept for a retention window (`virtualization.runtimeMigration.retention`, a week by default) rather than deleted, so work that turns out to be missing after the move can still be recovered. The controller takes it out of everything that finds an agent's volumes by label — the agent and mount labels go, so the warm pool, the storage migration, the orphan sweep and a StatefulSet's claims never see it — and marks it `retained-for` the Agent, with annotations naming the path it held and the time it is kept until. It is owned by the Agent, and the controller deletes it when the Agent is deleted or, from its periodic sweep, once the window has passed; a window that is not a readable time is kept and warned about, never read as expired. Because a StatefulSet claims volumes by name, an Agent put back on the container backend by hand is refused while anything is retained for it, rather than silently resuming from its pre-migration home. An operator recovers from a retained volume as the runbook below says, and ends the window early by deleting the claim.

**What the seed carries.** The copy is the home as one tree, entry by entry: names relative to `HOME`, modes, modification times to the second, symlinks as the links they are whatever they point at, a file with several names once, and a sparse file as its data and a map of its holes, which platform-init restores as holes again. Owners stay numeric, except that the uid and gid the install runs agent containers as become root's, the user a machine's harness runs as, so git and ssh accept what the agent owned; every other owner is kept. Extended attributes, ACLs, sockets, fifos and devices are not carried. What only the container used stays behind: the runtime's env file, which the platform pushes again when the machine's runtime first says hello, so no stale credentials land on the disk, and the container's link from `~/.cache` to pod-local scratch, so a machine keeps its caches in `HOME`. The copy Job walks the volumes within a bound on depth, entries and memory, and a home past one fails the copy with a message that names it. The runner drops an upload that sends nothing for minutes, because the upload holds the machine down; it flushes the seed and the share before it answers, and removes a seed a killed runner left half-staged at the machine's next action or when the seed is removed. platform-init flushes the restored home to the disk before it gives it its name, so a stop mid-seed never leaves a named but partial home.

### Operating a migration

A runbook for operators; every name below is the label or annotation the controller and api-server write.

**Find what is retained.** A retained volume carries the label `agent-platform.ai/retained-for` naming its Agent, and the annotations `agent-platform.ai/retained-mount` (the path it held) and `agent-platform.ai/retained-until` (an RFC 3339 time). List them with `kubectl get pvc -n <agent-namespace> -l agent-platform.ai/retained-for=<agent>`, or across Agents with `-l agent-platform.ai/retained-for`. Volumes of a migration that has not switched yet are not retained: they are still the Agent's own, labelled as any container Agent's volumes are.

**Read one, as hostile content.** The volume holds whatever the agent wrote, as root in its own sandbox, so treat it as untrusted: device nodes, setuid binaries and symlinks pointing anywhere on the host that mounts it.

- Mount it read-only, and with `nosuid,nodev,noexec`: set those in the PersistentVolume's mount options before a pod mounts it, and mount the claim read-only in the pod as well.
- Use a pod of your own, not the Agent's: a minimal image, no service-account token, no network beyond what the copy needs, running as a non-root user with every capability dropped. Never run anything from the volume.
- Never follow a symlink out of it. Copy links as links — `tar` without `-h`, `cp -P`, `rsync -l` without `-L` — and never resolve one while reading.
- Copy what you need into the Agent's `HOME` through the files API, or anywhere else, and delete the pod.

**Extend the window.** Overwrite the time with `kubectl annotate pvc <name> -n <agent-namespace> agent-platform.ai/retained-until=<RFC 3339 time> --overwrite`. A value that is not a readable time is kept and warned about, never read as expired, so a typo never deletes the only copy.

**Unstick a migration.** The Agent's `RuntimeMigrating` condition names the phase and why it waits, and the Agent's status counts the copy attempts. A migration that cannot finish fails on its own after three copy attempts or six hours. Until it is verified it can be aborted, which returns the Agent to the container on its old volumes, or, once failed, retried, which starts over with a fresh machine; the Agent's owner does either from the Agent's row. An operator without the UI withdraws the request by removing the `agent-platform.ai/runtime-migration` annotation and its `-target`, `-snapshot`, `-mounts` and `-retry` companions, which the controller treats as an abort; the spec was never switched, and the `-snapshot` annotation, read before it is removed, holds the fields as they were. A retry by hand sets `agent-platform.ai/runtime-migration-retry` to the current time. A verified migration cannot be aborted: the machine is the Agent now, and what the copy missed is recovered from the retained volumes.
