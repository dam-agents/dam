# Knowledge Bases

Last verified: 2026-09-25

## Overview

A **Knowledge Base** is an Agent that builds and maintains a body of knowledge the user works with through chat. The platform deliberately owns almost none of it: no ingestion pipeline, no query API, no knowledge schema. The behavior lives in the agent, and the platform provides only the structural shell — a way to create the pairing and a surface to list it.

Two pieces make an Agent a Knowledge Base:

- **The Agent Kind marker.** A create-time annotation on the Agent (`knowledge-base`), immutable afterwards, surfaced on the Agent view. A knowledge base *is* an agent, so it lists on Home beside every other one rather than on a destination of its own, badged by the kit that made it, and what the owner pays to run it is accounted for in the compute and spend figures there. Nothing about a knowledge base is routed or rendered separately any more: the destination, its create form and the paths they lived at are gone, and a marked agent opens, configures and deletes exactly as any other does. Everything else about the agent — lifecycle, sessions, connections, schedules, budgets — is a plain Agent.
- **The Install Command.** A one-shot shell command run in the Agent's workspace at create, which bootstraps the agent's knowledge tooling by running the toolkit's own `bootstrap.sh` from the checkout the kit seeds. No agent turn is involved — it is a workspace mutation, not a conversation. It is **declared by the starter kit** that is the KB template (`install.command` in the kit's `kit.yaml`, [starter kits](starter-kits.md#concepts)), so the server keeps no map from template id to command: a new procedure is a new kit. How a template's tooling reaches the chosen harness is the template's concern: every bootstrap is harness-aware, and the platform's whole contribution is the `PLATFORM_HARNESS` its harness images carry ([topology](platform-topology.md#agent-runtime)), naming the **harness family** the sandbox runs — the installer reads it, lands its manual, commands, and any skill where that harness reads them, and detects the harness itself when the variable is absent (a custom image). The first session stays template-agnostic for the same reason: it opens on the briefing the platform composes, which ends at the `ONBOARDING.md` the seed brought in, so the platform names no procedure of its own. The platform ships neither pointer nor tooling: the kit names the toolkit repository as its `seed`, the catalog refresh pins it to a commit, the seed brings that commit into the workspace, and the install runs what is already there — no network at install, and the toolkit version is the one the catalog resolved. The share roots the kit declares ride a create-time annotation stamp and are surfaced on the Agent view, so the sharing surfaces know what an agent publishes without asking which template built it. A knowledge base created before kits carries the old kind and template annotations instead, and keeps the roots that template always had, so nothing about it has to be migrated.

## Create flow

A knowledge base is a **regular starter kit that declares one capability**: the two KB templates are the kits `llm-wiki` and `plain-wiki`, each living in the toolkit repository it installs and reached through the curated catalog, each declaring `knowledgeBase.shareRoots` — the paths its share publishes — and its bootstrap as `install`, and shipping the `ONBOARDING.md` its first session is briefed to follow ([starter kits](starter-kits.md#concepts)). Creation is the kit apply, whoever starts it:

1. **Agent create** with the declared share roots stamped as a create-time annotation, the toolkit repository as the workspace seed (cloned at the commit the catalog resolved, ahead of everything below), passing the create choices through (harness image, provider, and catalog connections) on the trusted egress preset. The harness is the user's choice, the same catalogue coding agents pick from — not pinned to Claude Code. Each harness template may declare its **harness family** — which agent CLI runs inside the image, a closed vocabulary owned by the templates contract ([`packages/api-server-api/src/modules/templates/`](../../packages/api-server-api/src/modules/templates/)) and validated when templates load, so a misdeclared family rejects the template rather than degrading silently.
2. **Install Command delivery** over the `workspace-command` rail — a one-shot runtime-channel event alongside `workspace-seed`, on the same durable outbox schedules use ([runtime delivery](runtime-delivery.md#event-lifecycle), [schedules](schedules.md#fire)). The event survives the pod not being up yet — including an agent parked over budget — and is delivered once the agent is Ready. agent-runtime runs the command in the workspace, in the pod's environment, so egress rides the paired gateway exactly as a harness process would. It runs once: the plugin writes a sentinel on success, so a redelivery (or a pod killed mid-run before the outbox settled) never double-runs a completed install.
3. **Initialization session** queued behind it — the briefing the platform composes from the kit and the agent's live state — and the **wake**, so the freshly created agent comes up, runs the bootstrap and opens on its own `ONBOARDING.md` before the user does anything.

There is no knowledge-bases module left to create one: the kit apply is the only path, and the one piece of knowledge-base-specific code that survives is the share roots each retired template always had, kept so an agent stamped before kits still publishes what it always did. A Knowledge Base is exactly the owner's Agent plus the marker, and deleting the agent deletes the Knowledge Base.

## UI

There is no Knowledge Bases destination, no create form and no route of its own: a knowledge base is made by applying its kit, on the same setup page every other kit uses ([starter kits](starter-kits.md)), and it lists, opens and is configured on Home beside every other agent. What survives of the old surface is the capability, not the destination: an agent that publishes a knowledge base offers sharing from its chat, and it offers it whether the roots came from a kit or from the marker an older agent carries ([sharing](#sharing)).

A fresh KB **greets the user** with no browser involved: the apply queues an `initialization` event behind the Install Command on the same rail ([runtime-delivery](runtime-delivery.md#event)), carrying the briefing composed from the kit and the agent's state at that moment, and the agent-runtime opens a regular chat session with it once the install has run. The chat opens that session first while it is the agent's most recent one, so a fresh KB opens with the agent introducing itself rather than an empty chat. The greeting is a briefing rather than a bare command because setting a knowledge base up means asking its owner what it is for — and an agent that has to ask is one the platform holds as [not yet onboarded](starter-kits.md#concepts), reporting what it still needs as a checklist. The mechanism is shared with starter kits.

The greeting cannot race the bootstrap: the rail runs an agent's events in order and the Install Command's handler returns only when the command has finished, so the pod not being up yet, a wake that arrives late and a failed install retrying under the runtime channel's per-event attempt budget ([runtime-delivery](runtime-delivery.md)) all merely delay it. The hold is bounded, not absolute: an install that exhausts its budget, or lands on a runtime that cannot run it, is stamped settled-with-error with the reason the runtime reported, the agent shows the failure with a retry, and only then does the initialization turn open — against a KB whose `ONBOARDING.md` may be missing, which the briefing tells the agent to report and stop on rather than the agent staying unusable until the install event's TTL.

The create itself is compensated rather than transactional: the share roots are stamped by the agent create while the install event is enqueued after it, and a failed enqueue deletes the fresh agent and surfaces the failure — so an agent whose setup never ran can only arise if that compensating delete itself fails.

Lifecycle actions (wake, restart, pause, stop, delete) are the standard agent actions.

## Sharing

A knowledge base can be **shared** as a read-only MCP endpoint so other people's sandboxes query it without re-ingesting its sources. The platform stays out of the knowledge itself: what is shared is a **published snapshot** of the owner-selected top-level workspace directories (defaulted per KB template). The KB's own pod computes each publish — it walks the share roots (confined to them: symlinks resolving outside a root are excluded), content-hashes every text document, builds the segmented full-text index, and uploads through short-lived presigned upload URLs — while the api-server stays the authority: it authorizes the publish, mints every storage key, diffs against the previous snapshot so unchanged content carries forward without re-upload, verifies what landed, and commits the manifest as one atomic pointer swap. Serving never touches the agent: a snapshot keeps answering while the KB is hibernated, parked over budget, or stopped, and a failed republish leaves the last good snapshot serving. Snapshots replaced by a newer publish are garbage-collected after a grace hold — reachability spans the current snapshot and every replaced one still inside the hold; unsharing and agent deletion purge them.

The owner's handle is one **durable share string** (`kbshare_…`), re-copyable from the sandbox's Knowledge settings at any time; rotating it locks out every current holder, and re-sharing after unshare mints a fresh identity so old strings never revive. Reveal and rotate are browser-only operations — no agent-held credential can reach them, and the agent-facing tools (below) structurally cannot return the string. The secret is stored retrievably (the artifact-slug precedent, deliberately not the API keys' HMAC-only model) because durable re-copy is the product contract.

Consumption rides the connections model: pasting the string creates a hidden managed connection ([connections](connections.md)) that stores the per-share secret under a per-share header name, and one built-in aggregate MCP entry (`knowledge-bases`) appears in a sandbox while it holds at least one such grant. The entry points at the **in-cluster harness route** `/api/agents/:id/kb` — the same channel the agent already uses for platform-outbound — not the public share host, so consumer reads never leave the cluster and never traverse the egress gateway. Per request the platform authenticates the agent (as platform-outbound does), reads the shared-knowledge-base connections granted to it, and replays their per-share secrets into the stateless serving app; that app validates every replayed secret against the live share — the set of valid ones *is* the accessible set, so rotate and revoke cut access — and there is no user identity and no ACL beyond the grant. The same serving app is also reachable on the public share host as a by-link endpoint (used by the e2e and any external MCP client). Tools are content-agnostic retrieval only (list, read, index-backed search, grep) — read-only holds because no code path from a consumer request reaches an agent, its PVC, or any write rail; document reads resolve only through the snapshot manifest. No LLM runs in the serving path: consumers' own agents synthesize on their own credentials, so a query costs the owner nothing. Consumer-supplied grep patterns execute in a worker thread killed at a hard deadline, never on the event loop.

A shared snapshot describes itself through a **usage guide**: `list_knowledge_bases` returns a per-KB `guide` that the platform lifts verbatim (first 8000 characters) from a well-known `USAGE_GUIDE.md` at the top of the share's first root — `wiki/USAGE_GUIDE.md` for the plain-wiki template — falling back to a generic "look for an index to navigate" note when the file is absent. The guide is not platform machinery; it is just a file inside the shared tree, so keeping it useful is the KB agent's job: an agent-authored knowledge base should have that agent write and refresh a minimal, consumer-facing `USAGE_GUIDE.md` (what the KB covers, how it is laid out, which tool to reach for) as part of building the wiki, so the agents that query the snapshot can orient without blind trial and error. Nothing enforces the file — an unshared or guide-less KB simply serves the fallback.

Freshness is owned by the pod: it watches the shared folders recursively, and any edit — whoever made it — sets a dirty marker persisted on the agent volume and arms a quiet-period timer, after which the pod initiates the publish handshake with the api-server (inventory in, work order out, completion report back). The persisted marker means a pod that died dirty publishes shortly after its next boot with no server bookkeeping, and a scheduled or running publish holds the pod awake ([agent lifecycle](agent-lifecycle.md)). The api-server's remaining roles are delivery of the share's roots and limits to the pod (on share create, root changes, refresh, and wake) and a capability gate: a runtime too old to self-publish gets the share marked failed with an update-the-agent hint ([runtime delivery](runtime-delivery.md)). Publish outcomes push live hints to the owner's UI. Beyond that automatic path, an on-demand hard refresh republishes immediately, and it must be possible both manually by the owner and by the KB's own agent — the agent acts through platform MCP tools registered only on agents that publish a knowledge base, which also let it start sharing.

## Where the code lives

- Create: the kit apply, [`packages/api-server/src/modules/starter-kits/`](../../packages/api-server/src/modules/starter-kits/) — there is no knowledge-bases module of its own
- Kind marker plumbing, for the agents stamped before kits: [`packages/api-server/src/modules/agents/`](../../packages/api-server/src/modules/agents/)
- UI: [`packages/ui/src/modules/knowledge-bases/`](../../packages/ui/src/modules/knowledge-bases/) — sharing only. There is no create form, no route and no store action of its own: a knowledge base is listed, opened and configured as the Agent it is
- Sharing contract and implementation: [`packages/api-server-api/src/modules/kb-shares/`](../../packages/api-server-api/src/modules/kb-shares/), [`packages/api-server/src/modules/kb-shares/`](../../packages/api-server/src/modules/kb-shares/)
