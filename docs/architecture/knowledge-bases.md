# Knowledge Bases

Last verified: 2026-09-16

## Overview

A **Knowledge Base** is an Agent that builds and maintains a body of knowledge the user works with through chat. The platform deliberately owns almost none of it: no ingestion pipeline, no query API, no knowledge schema. Following the Experiments bet, the behavior lives in the agent, and the platform provides only the structural shell — a way to create the pairing and a surface to list it.

Two pieces make an Agent a Knowledge Base:

- **The Agent Kind marker.** A create-time annotation on the Agent (`knowledge-base`), immutable afterwards, surfaced on the Agent view. A Kind surfaces where its agents list — knowledge bases on their own destination, experiment agents badged among the coding agents while their surface is hidden; a knowledge base *is* an agent, so the Knowledge Bases destination is a filtered view onto the same agents rather than an exclusive home, and what the owner pays to run is accounted for across those destinations and the compute and spend figures on Home. Everything else about the agent — lifecycle, sessions, connections, schedules, budgets — is a plain Agent. The marker is shared machinery: [experiments](experiments.md) uses the same one, and both ride a shared kinded-create rail owned by the agents module.
- **The Install Command.** A one-shot shell command run in the Agent's workspace at create, which bootstraps the agent's knowledge tooling from an external installer. No agent turn is involved — it is a workspace mutation, not a conversation. It is **declared by the starter kit** that is the KB template (`install.command` in the built-in kit's `kit.yaml`, [starter kits](starter-kits.md#concepts)), so the server keeps no map from template id to command: a new procedure is a new built-in kit. How a template's tooling reaches the chosen harness is the template's concern: every bootstrap is harness-aware, and the platform's whole contribution is to export, through the variable the kit names (`install.harnessEnv`), which **harness family** the sandbox runs — the installer then lands its manual, commands, and any skill where that harness reads them, and detects the harness itself when no family is named (a custom image, or a template that declares none). Each template's bootstrap installs the onboarding command the kit's `onboarding.command` names, so the first session stays template-agnostic. The platform ships the pointer, never the tooling. The picked template id rides the same create-time annotation stamp as the Kind marker and is surfaced on the Agent view (opaque to the agents module — the knowledge-bases surface owns the id set), so the KB list can display which procedure a knowledge base came from; it is absent on knowledge bases created before it was recorded.

## Create flow

A knowledge base is a **regular starter kit with a marker**: the two KB templates are the built-in kits `platform/llm-wiki` and `platform/plain-wiki`, each declaring `knowledgeBase.template`, its bootstrap as `install`, and its onboarding command as `onboarding` ([starter kits](starter-kits.md#concepts)). Creation is the kit apply, whoever starts it:

1. **Agent create** with the Kind marker and the template id stamped as create-time annotations, passing the create choices through (harness image, provider, and catalog connections) on the trusted egress preset. The harness is the user's choice, the same catalogue coding agents pick from — not pinned to Claude Code. Each harness template may declare its **harness family** — which agent CLI runs inside the image, a closed vocabulary owned by the templates contract ([`packages/api-server-api/src/modules/templates/`](../../packages/api-server-api/src/modules/templates/)) and validated when templates load, so a misdeclared family rejects the template rather than degrading silently.
2. **Install Command delivery** over the `workspace-command` rail — a one-shot runtime-channel event alongside `workspace-seed`, on the same durable outbox schedules and Experiments use ([runtime delivery](runtime-delivery.md#event-lifecycle), [schedules](schedules.md#fire)). The event survives the pod not being up yet — including an agent parked over budget — and is delivered once the agent is Ready. agent-runtime runs the command in the workspace, in the pod's environment, so egress rides the paired gateway exactly as a harness process would. It runs once: the plugin writes a sentinel on success, so a redelivery (or a pod killed mid-run before the outbox settled) never double-runs a completed install.
3. **Initialization session** queued behind it — the onboarding command the kit names, which the bootstrap installed — and the **wake**, so the freshly created agent comes up, runs the bootstrap and opens on its onboarding command before the user does anything.

The owner-scoped knowledge-bases module keeps two things: the **form's create**, an adapter that finds the built-in kit declaring the picked template and applies it with the form's choices (kept until the form retires in favour of the kit setup), and the default share roots per template. The module has no persistence of its own: a Knowledge Base is exactly the owner's Agent plus the marker, and deleting the agent deletes the Knowledge Base.

## UI

Knowledge Bases is a feature-gated destination ([features](features.md)) with a list and a **standalone per-KB page** — the chat surface under the knowledge base's own route, so the rail keeps the Knowledge Bases context and leaving returns to the KB list, never to Agents. Creation **is** its own form: a single page asking for a name, a KB Template, a harness, a provider and connections — the harness and provider choices coding agents get, sharing their catalogue, default selection, and loading/failed/empty presentation, with the toolkit template and Claude Code preselected. A persisted draft whose harness is no longer in the catalogue is reconciled to the default when the catalogue arrives. Every KB template works on every catalogue harness, so nothing in the form is gated on the pairing. Both the KB list's create button and the Home entry card land on it directly, and submitting dispatches to this module's create — see [agent-lifecycle](agent-lifecycle.md#create).

A fresh KB **greets the user** with no browser involved: its create queues an `initialization` event behind the Install Command on the same rail ([runtime-delivery](runtime-delivery.md#event)), carrying the template's onboarding command in the form the KB's harness expands installed commands under — the command name comes from the built-in [starter kit](starter-kits.md) that declares the template (`onboarding.command` in its `kit.yaml`, read through a port; a template no kit declares opens idle), the spelling from the chosen template's harness family at create — and the agent-runtime opens a regular chat session with it once the install has run. The chat opens that session first while it is the agent's most recent one, so a fresh KB opens with the agent introducing itself rather than an empty chat. This is why every template's bootstrap installs that command. The mechanism is shared with experiments and starter kits; a knowledge base created from its kit gets the same turn from the kit's own initialization.

The greeting cannot race the bootstrap: the rail runs an agent's events in order and the Install Command's handler returns only when the command has finished, so the pod not being up yet, a wake that arrives late and a failed install retrying under the runtime channel's per-event attempt budget ([runtime-delivery](runtime-delivery.md)) all merely delay it. The hold is bounded, not absolute: an install that exhausts its budget, or lands on a runtime that cannot run it, is stamped settled-with-error and the initialization turn still opens — against a KB whose onboarding command may be missing, which the harness reports as an unknown command rather than the agent staying unusable until the install event's TTL.

The create itself is compensated rather than transactional: the marker is stamped by the agent create while the install event is enqueued after it, and a failed enqueue deletes the fresh agent and surfaces the failure — so a marked agent whose setup never ran can only arise if that compensating delete itself fails.

Lifecycle actions (wake, restart, pause, stop, delete) are the standard agent actions.

## Sharing

A knowledge base can be **shared** as a read-only MCP endpoint so other people's sandboxes query it without re-ingesting its sources. The platform stays out of the knowledge itself: what is shared is a **published snapshot** of the owner-selected top-level workspace directories (defaulted per KB template). The KB's own pod computes each publish — it walks the share roots (confined to them: symlinks resolving outside a root are excluded), content-hashes every text document, builds the segmented full-text index, and uploads through short-lived presigned upload URLs — while the api-server stays the authority: it authorizes the publish, mints every storage key, diffs against the previous snapshot so unchanged content carries forward without re-upload, verifies what landed, and commits the manifest as one atomic pointer swap. Serving never touches the agent: a snapshot keeps answering while the KB is hibernated, parked over budget, or stopped, and a failed republish leaves the last good snapshot serving. Snapshots replaced by a newer publish are garbage-collected after a grace hold — reachability spans the current snapshot and every replaced one still inside the hold; unsharing and agent deletion purge them.

The owner's handle is one **durable share string** (`kbshare_…`), re-copyable from the sandbox's Knowledge settings at any time; rotating it locks out every current holder, and re-sharing after unshare mints a fresh identity so old strings never revive. Reveal and rotate are browser-only operations — no agent-held credential can reach them, and the agent-facing tools (below) structurally cannot return the string. The secret is stored retrievably (the artifact-slug precedent, deliberately not the API keys' HMAC-only model) because durable re-copy is the product contract.

Consumption rides the connections model: pasting the string creates a hidden managed connection ([connections](connections.md)) that stores the per-share secret under a per-share header name, and one built-in aggregate MCP entry (`knowledge-bases`) appears in a sandbox while it holds at least one such grant. The entry points at the **in-cluster harness route** `/api/agents/:id/kb` — the same channel the agent already uses for platform-outbound — not the public share host, so consumer reads never leave the cluster and never traverse the egress gateway. Per request the platform authenticates the agent (as platform-outbound does), reads the shared-knowledge-base connections granted to it, and replays their per-share secrets into the stateless serving app; that app validates every replayed secret against the live share — the set of valid ones *is* the accessible set, so rotate and revoke cut access — and there is no user identity and no ACL beyond the grant. The same serving app is also reachable on the public share host as a by-link endpoint (used by the e2e and any external MCP client). Tools are content-agnostic retrieval only (list, read, index-backed search, grep) — read-only holds because no code path from a consumer request reaches an agent, its PVC, or any write rail; document reads resolve only through the snapshot manifest. No LLM runs in the serving path: consumers' own agents synthesize on their own credentials, so a query costs the owner nothing. Consumer-supplied grep patterns execute in a worker thread killed at a hard deadline, never on the event loop.

A shared snapshot describes itself through a **usage guide**: `list_knowledge_bases` returns a per-KB `guide` that the platform lifts verbatim (first 8000 characters) from a well-known `USAGE_GUIDE.md` at the top of the share's first root — `wiki/USAGE_GUIDE.md` for the plain-wiki template — falling back to a generic "look for an index to navigate" note when the file is absent. The guide is not platform machinery; it is just a file inside the shared tree, so keeping it useful is the KB agent's job: an agent-authored knowledge base should have that agent write and refresh a minimal, consumer-facing `USAGE_GUIDE.md` (what the KB covers, how it is laid out, which tool to reach for) as part of building the wiki, so the agents that query the snapshot can orient without blind trial and error. Nothing enforces the file — an unshared or guide-less KB simply serves the fallback.

Freshness is owned by the pod: it watches the shared folders recursively, and any edit — whoever made it — sets a dirty marker persisted on the agent volume and arms a quiet-period timer, after which the pod initiates the publish handshake with the api-server (inventory in, work order out, completion report back). The persisted marker means a pod that died dirty publishes shortly after its next boot with no server bookkeeping, and a scheduled or running publish holds the pod awake ([agent lifecycle](agent-lifecycle.md)). The api-server's remaining roles are delivery of the share's roots and limits to the pod (on share create, root changes, refresh, and wake) and a capability gate: a runtime too old to self-publish gets the share marked failed with an update-the-agent hint ([runtime delivery](runtime-delivery.md)). Publish outcomes push live hints to the owner's UI. Beyond that automatic path, an on-demand hard refresh republishes immediately, and it must be possible both manually by the owner and by the KB's own agent — the agent acts through platform MCP tools registered only on knowledge-base-kind agents, which also let it start sharing.
