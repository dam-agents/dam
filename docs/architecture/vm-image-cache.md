# VM image cache

Last verified: 2026-09-27

A machine may reach only its gateway, so its image is fetched for it and unpacked into a tree every machine of that image mounts read-only. Where that tree lives is the one part of the runner's storage an install may move off its claim.

By default each owner's runner caches on its own volume, so the same few harness images are fetched once per owner. An install that would rather pay once per node points `imageCache.hostPath` at a host directory every runner scheduled there shares — not a `ReadWriteMany` claim, the costliest class, which buys only cross-node dedup. On OpenShift the runners then need an SCC that admits a host directory, which the chart's own does not — and one that leaves the SELinux type to the pod: SELinux confines every container to a type that may neither write nor read a directory the kubelet creates on the host, so the image cache service runs there as the unconfined container type at the plain level and labels the directory for containers as it opens the cache. Every tree it unpacks inherits that label, which is what lets the runners, still confined, boot from it; the label is set from the chart's OpenShift signal, and a service that cannot set it says so and exits rather than serve trees no runner could read.

**Every cache has exactly one writer.** On a runner's own volume that is the runner. On a node directory it is a per-node **image cache service**: runners mount the directory read-only and ask the service, over a socket inside it, for each image a machine boots. The service resolves the reference, fetches and unpacks it on a miss with the pull secrets the runner forwards for that machine ([security-and-credentials](security-and-credentials.md#image-pull-credentials)), and answers with the tree and what the image says to run. A runner that could write a shared directory would let a guest that escapes into it rewrite a tree another owner's machines boot; one writer also means a fetch and an eviction never have to agree across processes, so what the writer knows about the cache is kept in its memory — all but where each tree came from, which is written beside the tree because a later caller's access is checked against it. The service is therefore in the boot path: with it down, a runner boots only an image one of its own machines already holds, and refuses any other as unavailable rather than booting it straight from the registry. The service unpacks with every capability dropped but the few that restoring an image's owners and modes takes, and skips the image's `/dev`, so no tree carries a device node.

**An entry is named by the image it holds, not by the reference that asked for it.** A create resolves its reference to a digest and boots the tree stored under it, so two tags of one image share a tree and a mutable tag is never frozen at what it first named. The writer remembers what a tag resolved to for a few minutes; a pinned digest is never resolved, and a registry that cannot answer boots what the tag last resolved to. A machine records the digest it booted, which is how its runner knows, even after a restart, which tree it holds once the tag moves on. Every registry read names the host's platform, so a tag resolves to that platform's own image rather than to a multi-arch index, and each tree records the platform it was unpacked for: a claim that moves to a node of another architecture fetches a pinned index digest again rather than booting a tree it cannot run.

**A tree is either whole under its name or not there.** A fetch unpacks into a scratch tree, flushes it to disk and only then renames it into place; an eviction renames the tree away before it deletes it. A writer that dies mid-fetch or mid-eviction leaves only a scratch tree, which the next open reclaims, never a partial tree a lookup would take as complete. A fetch that finds an incomplete tree, or another platform's, under its name moves it aside and puts its own in place. A resolve has one deadline for everything it does, fetch included, and a runner waits a little past it, so a service that is slow is told apart from one that is gone — only one that is gone lets a runner boot a tree it already holds. A fetch that fails for its image — a registry refusing the export, a stream tar cannot unpack — is reported as an unavailable image, and a disk that fills, or has less room than the image's manifest names before the download starts, as a lack of capacity, never as a boot to retry at once into the same state.

**Eviction never frees a tree a machine is running from.** It takes the oldest write first, down to a byte count the install states, sparing what is held. A runner holds the digests its machines boot by naming them again every minute, and a hold lapses only once nobody names it — a runner that stopped has no machines left. A hold only extends, so no runner can release what another holds, and only a tree on disk is held, so a resolve that fails holds nothing; past half again its budget, the service fetches nothing. Each fetch under way counts toward that ceiling at the compressed size its manifest names, so fetches that start together cannot each find the cache under it. A service that restarts has forgotten every hold, so it evicts nothing until the runners have had time to name theirs again.

**Nothing could fill that cache before an agent needed it.** A runner exists only once its owner's agents need one, so the first machine on an image, on every node after every deploy, would wait out the fetch with a user watching. The service therefore preloads the harness images the install ships, resolving their tags on every pass, and pins them against eviction. That set is fixed at deploy, so a custom agent image is never among them. It preloads with the install's default pull secrets, mounted into it, so an image only a per-template secret reads is fetched when a machine first needs it.

**A private entry is checked per machine.** A shared cache would hand one owner's fetch to every owner naming the image, so an entry an anonymous read could not reach is served only to a machine whose own pull secrets read its manifest in a repository the entry was fetched from. The repository a caller names is never what is asked, because anyone can name any digest under a registry of their own that answers every read; a caller naming the digest in a repository it was never fetched from proves its access by fetching it from there, and that repository then joins the entry's origins. A read with no credential is anonymous even where the service's own environment holds one. An anonymous read of an origin that succeeds marks the entry public, and only an entry not known to be public needs the registry to boot. The service keeps that knowledge in memory, so after a restart it asks again. The check gates a boot, not a read. A runner's own cache serves one owner and checks nothing.

**What a runner may read on a node cache is not gated.** Its mount is the whole directory, so any runner on the node — and any guest that escapes into one — reads every cached tree, other owners' private images included. The per-machine access check decides only what the service resolves and fetches for a caller. The socket cannot tell one runner from another either, since every runner is root on the node, so what a caller can make the service do is bounded instead of attributed: a hold names only trees on disk, at most a thousand per call, and once holds keep the cache past half again its budget, it refuses every fetch, as a capacity problem, and logs an error for the operator.
