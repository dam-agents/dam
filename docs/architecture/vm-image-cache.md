# VM image cache

Last verified: 2026-09-24

A machine may reach only its gateway, so its image is fetched for it and unpacked into a tree every machine of that image mounts read-only. Where that tree lives is the one part of the runner's storage an install may move off its claim.

By default each owner's runner caches on its own volume, so the same few harness images are fetched once per owner. An install that would rather pay once per node points `imageCache.hostPath` at a host directory every runner scheduled there shares — not a `ReadWriteMany` claim, the costliest class, which buys only cross-node dedup. On OpenShift the runners then need an SCC that admits a host directory, which the chart's own does not — and one that leaves the SELinux type to the pod: SELinux confines every container to a type that may neither write nor read a directory the kubelet creates on the host, so the image cache service runs there as the unconfined container type at the plain level and labels the directory for containers as it opens the cache. Every tree it unpacks inherits that label, which is what lets the runners, still confined, boot from it; the label is set from the chart's OpenShift signal, and a service that cannot set it says so and exits rather than serve trees no runner could read.

**Every cache has exactly one writer.** On a runner's own volume that is the runner. On a node directory it is a per-node **image cache service**: runners mount the directory read-only and ask the service, over a socket inside it, for each image a machine boots. The service resolves the reference, fetches and unpacks it on a miss with the pull secrets the runner forwards for that machine ([security-and-credentials](security-and-credentials.md#image-pull-credentials)), and answers with the tree and what the image says to run. A runner that could write a shared directory would let a guest that escapes into it rewrite a tree another owner's machines boot; one writer also means a fetch and an eviction never have to agree across processes, so nothing about the cache is kept in files beside it. The service is therefore in the boot path: with it down, a runner boots only an image one of its own machines already holds, and refuses any other as unavailable rather than booting it straight from the registry.

**An entry is named by the image it holds, not by the reference that asked for it.** A create resolves its reference to a digest and boots the tree stored under it, so two tags of one image share a tree and a mutable tag is never frozen at what it first named. The writer remembers what a tag resolved to for a few minutes; a pinned digest is never resolved, and a registry that cannot answer boots what the tag last resolved to. A machine records the digest it booted, which is how its runner knows, even after a restart, which tree it holds once the tag moves on.

**Eviction never frees a tree a machine is running from.** It takes the oldest write first, down to a byte count the install states, sparing what is held. A runner holds the digests its machines boot by naming them again every minute, and a hold lapses only once nobody names it — a runner that stopped has no machines left. A hold only extends, so no runner can release what another holds; past half again its budget, the service fetches nothing. A service that restarts has forgotten every hold, so it evicts nothing until the runners have had time to name theirs again.

**Nothing could fill that cache before an agent needed it.** A runner exists only once its owner's agents need one, so the first machine on an image, on every node after every deploy, would wait out the fetch with a user watching. The service therefore preloads the harness images the install ships, resolving their tags on every pass, and pins them against eviction. That set is fixed at deploy, so a custom agent image is never among them. It preloads with the install's default pull secrets, mounted into it, so an image only a per-template secret reads is fetched when a machine first needs it.

**A private entry is checked per machine.** A shared cache would hand one owner's fetch to every owner naming the image, so an entry an anonymous read could not reach is served only to a machine whose own pull secrets read its manifest. An anonymous read that succeeds marks the entry public, and only an entry not known to be public needs the registry to boot. The service keeps that knowledge in memory, so after a restart it asks again. The check gates a boot, not a read. A runner's own cache serves one owner and checks nothing.

**What a runner may read on a node cache is not gated.** Its mount is the whole directory, so any runner on the node — and any guest that escapes into one — reads every cached tree, other owners' private images included. The per-machine access check decides only what the service resolves and fetches for a caller. The socket cannot tell one runner from another either, since every runner is root on the node, so what a caller can make the service do is bounded instead of attributed: a hold names only trees on disk, at most a thousand per call, and once holds keep the cache past half again its budget, it refuses every fetch, as a capacity problem, and logs an error for the operator.
