# Starter Kits

Last verified: 2026-09-21

## Overview

A **Starter Kit** is a proven way of working applied to a *new* Agent: the connections, channels and schedules a job needs, optionally its own agent image, and an onboarding step that asks only for what the user alone can supply. It is not an Agent and not a Template ([ubiquitous language](../ubiquitous-language.md#starter-kits-bounded-context--in-design-3576-3638)). Templates are the platform's **harness catalog** — the images the platform itself delivers — and a kit is self-sufficient: it either runs on a harness the user picks from that catalog, or brings its own image.

Kits are **files in git, never rows in the cluster**. A kit is a `kit.yaml` at the root of the repository that holds it — for an agent definition such as Code Guardian, the definition repository *is* the kit. The platform reads **several named Kit Catalogs** through one reader, in a fixed order: the **built-in catalog** (`platform`), whose files ship inside the chart under `helm/starter-kits/` and are mounted into the api-server as a directory, so it is versioned with the release and needs no network; and any number of external catalogs, each a public git repository holding a `catalog.yaml` index of kits pinned to refs. A kit is addressed as `<catalog>/<kit>`, so two catalogs may ship a kit of the same id without one hiding the other. The api-server keeps only a **resolved snapshot** of each catalog in Postgres (`starter_kit_catalog_entries`), rewritten by the refresh job and rebuildable from the catalogs at any time; an Agent remembers only `<catalog>/<kit>@<version>`.

This is the V1 cut: a snapshot at create. Nothing tracks the kit's source afterwards, there is no backup and no automatic update. The increments that follow — a read-only definition, work-dir backups, and a detect-and-update path — are each additive to this page.

```mermaid
flowchart LR
  catalog[(kit catalog<br/>git, pinned refs)]
  kitrepo[(kit repository<br/>kit.yaml + ONBOARDING.md)]
  ui[ui]
  api[api-server<br/>starter-kits]
  agents[agents]
  schedules[schedules]
  channels[channels]
  pod[agent pod]

  api -->|read catalog.yaml, kit.yaml at ref| catalog
  catalog -.->|entry| kitrepo
  ui -->|kits.list / kits.create| api
  api -->|create + grants + kit stamp| agents
  api -->|create declared schedules| schedules
  api -->|bind Slack conversation| channels
  api -->|workspace-seed: definition at its commit| pod
  api -->|install, then initialization event| pod
  pod -.->|follows ONBOARDING.md in the checkout| kitrepo
```

## Concepts

- **Catalog refresh** — external catalogs are **moving**: adding a kit to one must not require redeploying the platform. A BullMQ periodic job re-reads every catalog on an interval, resolves each entry that names no ref (and each that names a branch or tag) to a **commit sha**, scans the definition for bundled skills, and **writes the resolved set to Postgres**. That job is the only thing that touches the network; every api-server serves kits by reading the table. The consequences are deliberate: an unpinned catalog still yields exact, immutable kits; a kit read is a local query rather than a fan-out of GitHub requests; the resolved rows carry the provenance a later Kit Pull needs to diff against; and a catalog that goes unreachable leaves the last good resolution serving rather than emptying the page. The same holds per entry, with one distinction: a catalog's rows are replaced only from a read in which every entry could be read; when an entry is unreadable — its ref does not resolve, its `kit.yaml` cannot be fetched, the source throws — the ones that resolved are updated and the unreadable ones keep their stored row, so a rate-limited pass never empties the list. An entry that was read and rejected — a `kit.yaml` the schema refuses, a path that escapes the catalog — is a withdrawal, not an outage: it leaves the resolved set like an entry the author removed, so one permanently broken kit never freezes the prune for the rest. The built-in catalog is refreshed from its mounted files by the same job, stamped with the release rather than a sha, because chart files have no commit to resolve. What lives where follows from that: the built-in catalog holds the **workload kits**, whose images this repository builds and whose kit files are versioned with the release, and the **definition kits** live in a curated catalog repository the install points at — `curated` by default. A definition kit is not copied into that catalog either: its `kit.yaml` sits at the root of the repository holding the code it installs, and the catalog lists it by `gitUrl`. That is what keeps the two in step — a change to a toolkit's bootstrap and the change to the kit describing it are one commit and one review, in the repository that owns both. Such a kit's seed says `self: true` rather than repeating the URL, and names no ref, so the workspace is seeded from the very commit the kit was resolved at and a kit can never describe code it was not read with. A seed names exactly one of `url` or `self`, so "seed this repository" is something the file says outright rather than something a reader infers from an absence. A definition kit is mostly a pointer at a repository that moves on its own cadence, so pinning it to a chart release would only mean a redeploy every time it changed.
- **Kit Catalog** — a named index the install reads kits from. The chart renders the list: the built-in catalog as a mounted directory when enabled, then each external catalog as a repository URL with an optional `ref` and `dir`. **A version is written in one place and one way.** Wherever a repository is named — a catalog in the chart's values, an entry in a `catalog.yaml`, a kit's `seed` — it is a plain `url` and an optional `ref`, and the same three words mean the same thing at every level. A URL that carries a version instead, as a `#ref` fragment or a `/tree/<ref>/<dir>` path, is **refused** rather than read at the default branch: the alternative is an install that pinned a version, silently got the tip, and never finds out. Entries are either a path inside the catalog or an external repository plus pinned ref. External catalogs are fetched anonymously over the public raw-file endpoint, so they and their kit repositories must be public; results are cached for a few minutes. A built-in kit can be switched off per install (`starterKits.builtin.kits.<id>.enabled`), the same switch the workload Templates had: the chart then leaves the kit out of the rendered catalog, so an image the install does not build never reaches the UI. A kit that brings its own image can also be pointed at another ref per install (`starterKits.builtin.kits.<id>.image`, swapped into the kit's `image.ref` at render): the local cluster uses it to run the workload kits on the images this checkout builds, and its install builds and loads the image of every enabled kit that names a local `platform-*` tag, exactly as it does for the harness Templates. The built-in catalog's workload images carry the same `@ci-pin` marker the chart uses for its own images, rewritten to the release's source sha by the same publish step, so the versioning mechanics are unchanged — only the declaration moved from Helm values into kit files.
- **Kit Schema** — the Zod schema in the contract package is the one source of truth; `kit.yaml` carries a `schemaVersion`. A kit that fails validation is dropped from the listing with a logged reason, never applied half-parsed. A duplicate id keeps the first.
- **Connection Requirement** — what a kit *accepts*: a set of Connection Templates or **connection families** (`github`, `github-enterprise`, …, the same groups the connection catalog shows as one connect page), required or suggested, plus a note. A family expands to every template in it, so `accepts: [github]` is satisfied by an OAuth, PAT or App connection and its Connect button opens the GitHub page with all methods; a kit that must insist on one method names the template instead. Families are declared on the Connection Templates themselves ([connections](connections.md#connection-template)) and carried on the template view, so the server-side check and the catalog UI read the same data.
- **Kit Schedule** — declared with the author's defaults and created by the platform at apply; a suggested one is created **disabled**. The apply form lists them with their cadence and lets the user **skip** any before create; onboarding never asks for cadence, and the user edits the rest on the instance.
- **Kit Channel** — suggested only. A channel never blocks apply; the apply form offers the Slack picker, other messengers are a note onboarding repeats.
- **Provider compatibility** — a provider is required of every Agent, so a kit never states it as a Connection Requirement: it lists the provider presets it supports in `providers` (a kit with its own image states them on the image instead, where they describe what that image can run on). The requirement list is for the connections the *job* needs, and the Connections section shows only those; a kit from an external catalog that still declares a provider under `accepts` is read as its provider list and kept out of that section, so the picker and the section never disagree about what is on offer. The apply form narrows the provider picker twice: to the kit's provider list, and to the **providers the chosen Template declares** it can run on — or, for a kit with its own image, the providers the kit declares for it (a Helm-declared list on each Template, validated at load — Claude Code images on Anthropic or the LiteLLM proxy, Codex on OpenAI or the proxy, Bob on its gateway or the proxy, Pi on any of the three). A Template that declares none narrows nothing. An empty intersection blocks create with a message rather than offering a provider the image cannot use.
- **Harnesses** — a kit without its own image may name the harness families it runs on (`harnesses: [claude-code, bob]`); the apply form then offers only Templates of those families, and says so when none is installed. Templates are the platform's harness catalog: Helm declares only harness images (`harnessTemplates`), never workloads.
- **Own image** — optional. A kit for a workload baked into a custom image (the research frameworks) names the image itself — an OCI reference, the harness family inside it, and the providers it can run on — and the harness choice disappears from the apply form. The Agent is created on that image exactly as a custom-image agent is, with the install's default mounts; nothing has to be declared in Helm for a kit to work. A kit without an image runs on whichever harness Template the user picks. The former `preconfigured` Templates are now kits in the built-in catalog: workload images belong in kits, harness images in Templates.
- **Install Command** — optional `install.command`: shell the agent-runtime runs once in the new agent's workspace, queued as a `workspace-command` event right after create and before anything else the apply queues, so a bootstrap has run by the time the initialization session opens. The command runs as the kit wrote it: every harness image states the family it runs in `PLATFORM_HARNESS` (`claude-code`, `codex`, `pi`, `bob`), set as an image `ENV` so the harness, the install command and terminal shells all inherit it; a bootstrap reads that instead of being told, and detects the harness itself on an image that carries none. The command runs **inside the agent's own sandbox** — the same pod, grants and egress rules under which the harness already executes whatever the kit's `ONBOARDING.md` asks of it — so a kit from any catalog may declare one; what it can never do is widen the platform-enforced boundary (the invariant below). This is how the two wiki kits run their toolkit's bootstrap: from the checkout their `seed` brought in, pinned to the commit the catalog resolved, instead of fetching a script from the network at install.
- **Knowledge Base Kit** — optional `knowledgeBase.shareRoots`: a kit may declare that what it creates publishes a [knowledge base](knowledge-bases.md), naming the workspace paths its shares expose. The apply stamps those roots on the Agent and nothing else changes: the toolkit is the kit's `seed`, the bootstrap its `install` run from that checkout, the first session its `onboarding`, so a knowledge base is a regular kit that declares one capability. No Kind marker is stamped — an agent created this way is badged by its kit like any other, and the sharing surfaces read the roots off the agent instead of asking which template built it; an agent stamped before kits keeps the old kind and template annotations and the roots that template always had. The two knowledge kits (LLM Wiki, Plain Wiki) live in the toolkit repositories they install and are reached through the curated catalog. They are the kits with no image of their own — they run on a harness the user picks — and each ships an `ONBOARDING.md` instead of naming a command, so the initialization session opens on the composed briefing once `install` has run and the intake is reported as a checklist. LLM Wiki keeps `/wiki-onboard` in its toolkit for a re-run; Plain Wiki's greeting moved into its `ONBOARDING.md` wholesale.
- **Kit Size** — optional `resources`: the CPU and memory limits and the workspace disk the kit's workload needs, plus a `note` saying why. It is stated in the user-facing vocabulary and nothing else: limits are what an agent's power and its owner's Ceiling are measured in, so a kit never states requests — the controller derives those from the limits. Each dimension is independent and a stated one wins over the harness Template's own value, so a kit sizes its workload whether it brings an image or runs on a picked harness; an omitted dimension inherits the Template's, then the install default. CPU and memory stay editable on the Agent afterwards like any other Size; disk is fixed at create. This is where the sizing the `preconfigured` Templates used to carry now lives.
- **Seed** — optional `seed: { url, ref, into }`: the kit's definition repository. The catalog refresh resolves the ref to a commit and records it beside the declared ref (`seed.commit`), and apply hands both to the agent create as its workspace seed, so the `workspace-seed` event brings the repository in at that commit **on that branch**, tracking `origin/<ref>` — the same rail a plain create's `gitRepo` rides — ahead of `install` and the initialization session. `into` says where: `work` (the default — the toolkit-as-workspace shape the wiki kits use) or `home` (a definition that wants to be `$HOME`, with `CLAUDE.md`, `scripts/` and `docs/` beside the platform's own dotfiles and `work/` as its git-ignored data directory — Code Guardian's shape). A home seed is never a clone: init, fetch, hard-reset of tracked paths, checkout of the branch, so nothing the platform or harness put in `$HOME` is removed. The seed first lists its destination as a git `safe.directory` in the agent's gitconfig — the home directory is the volume's mount root, owned by root, and git otherwise refuses to treat it as a repository, for the seed and for every `git` the agent later runs there. A private definition needs the GitHub connection the kit requires: the clone rides the gateway like any `git` in the pod. The work directory *is* the definition afterwards, so a seeded kit's `install` runs inside that checkout. A seed that fails is loud, not silent: the initialization session waits behind it, the runtime reports the reason, the agent shows it with a retry ([runtime delivery](runtime-delivery.md#event)), and the briefing tells the agent that a missing checkout means the seed failed — say so and stop, never clone or delete anything itself. The seed marks its own completion, so an agent's own clone in the work directory is never mistaken for it.
- **Bundled Skill** — a skill that lives in the kit's own definition repository. `kit.yaml` declares only a **scan root** (`bundledSkills.path`); the name and description come from each `SKILL.md`'s front matter, read at the kit's resolved commit, so the catalog can never advertise a stale description. The scan reuses the same reader public Skill Sources use. It is declared for display only: the setup page lists it so a user sees what the agent will be able to do, and the platform installs nothing — the harness discovers it as a file in the seeded definition. Keeping it in a separate field from `skills` is what guarantees the Skill Set apply never tries to install one.
- **Initialization Session** — the first turn is an `initialization` event on the [runtime-delivery](runtime-delivery.md#event) rail, not a chat message a browser sends — the same event a knowledge base's or an experiment's create queues for its onboarding command, so every platform-created agent gets its first session the same way. Apply composes the turn once the grants, schedules and Slack binding it describes exist, inserts the event, and wakes the agent; the agent-runtime opens a **regular** chat session with it — regular, not schedule-typed, so the user finds it in the default session list and can answer what it asks. The session it opens is marked `initialization` in its platform metadata, so the agent's chat opens it first for as long as it is the agent's most recent session — whether or not anything is held — and the session list badges it **Onboarding** while the kit's onboarding is pending. Running once is the rail's guarantee, not the kit's: the event id `initialization:<agent>:<ts>` is deduped by the runtime's per-key ledger on the agent's own volume, a failed dispatch is redelivered until it succeeds, and none of it needs a browser open. The turn used to be sent by the UI on first open, guarded by a per-page ref and the session list; the list is empty for the window between sending and the harness reporting the session, so a reload in that window produced two sessions. Kinded creates use the same rail for their install bootstrap, and events run in order, so a kit's bootstrap lands before its initialization session opens. **What the session opens with is the kit's `onboarding` field**: absent, the platform-composed briefing (follow `ONBOARDING.md` when the kit has a seed, ask the user what to work on otherwise); `prompt`, that text in place of the default instruction; `command`, a harness command the kit names and the platform spells for the agent's harness (`/wiki-onboard`, `/prompts:wiki-onboard` on Codex) — a mechanical trigger, so a kit that needs its first turn to ask the user for something declares none and ships `ONBOARDING.md`; `false`, no event and no session — the agent starts idle the way a Template-created one did.
- **Kit Onboarding State** — onboarding is a **gate composed on top of the initialization session**, not the session itself: the session is the mechanism every platform-created agent shares; the gate is the kit-only hold on schedules, the tools that report progress and completion, and the UI state that shows them. An Agent created from a kit is **not fully configured** until its onboarding turn says otherwise. The onboarding prompt tells the agent to call the `mark_onboarding_complete` platform MCP tool once the configuration is genuinely in place, and the api-server stamps the completion time as an annotation on the Agent. The stamp is announced on the owner's live channel as an agents hint — the one a create or a runtime hello raises — so an open UI drops the Onboarding tag at once rather than on its next incidental refresh; `AgentUpdated` carries the owner whenever its emitter knows one, and the hint saga routes it only then, so an emitter that wants the UI to move names the owner. **The tools are registered only while onboarding is pending** — the same null-gating the knowledge-base tools use — so they cost an agent nothing in context for the rest of its life, and the check is free because the agent resolution that authenticates every MCP session already reads the Agent's annotations. They disappear at the session's next roll-over after completion, bounded by the session TTL; the mark is idempotent, so a stale session calling it changes nothing. The state says **the agent has not yet reported itself set up**, and is not derived from what the apply happened to create: a kit that declares no schedules — both knowledge kits — still wears the tag and still gets the tools, because what the checklist reports is the conversation with the user, which such a kit has like any other. Deriving it from the schedule count instead made the two knowledge kits, whose whole job is an intake conversation, the only kits that could not report one. The hold is what *follows* from the state for an agent that has schedules, so the briefing's release paragraph says what is true for the agent in front of it — the schedules are held, or the tag stays until it is released. An Agent is **stamped onboarded at create** only when no briefing opens: a kit that opted out (`onboarding: false` — every built-in workload kit, whose brief is the user's first prompt rather than an intake), or one whose onboarding is a bare harness command. That last one is a mechanical trigger with nothing to read, so it can never be asked for the release; leaving it pending would hold its schedules for good. Such an agent never wears the tag and never sees the tools. Re-running onboarding, when that surface exists, means clearing the annotation — which re-registers the tools on the next session. Until then the scheduler **holds every schedule on that agent**: the occurrence is skipped, the next one is computed and queued as normal, and the schedule records `held: onboarding not complete` as its last result — so a half-configured agent never does the wrong work on a cadence, and the cadence itself is not lost. The state is an annotation rather than a status condition because the api-server writes it and the controller never reconciles on it — `status` documents the controller as its sole writer. **Progress is the agent's to report.** The briefing has it open with `set_onboarding_checklist` — what it needs *from the user*, one step per value only they can supply, decision only they can make or action only they can take; never the agent's own work — which it may call again to add, rename or drop steps as the conversation evolves (steps it keeps stay ticked), and tick each with `complete_onboarding_step` as the user supplies it. The checklist is a JSON column on the agent's Postgres row, written only through these tools and gone with the agent; it rides the agent view as `onboardingSteps`, and every write raises the same agent-change hint as the stamp. The platform verifies no step — only the completion stamp gates schedules — so the checklist has the standing of the agent's own word, the same standing `mark_onboarding_complete` has. The agents list shows the state as a kit-purple **Onboarding** tag on the row — **Onboarding 2/5** once the agent has set a list — and the chat carries a bar above the composer naming the kit and the fraction; hovering either opens the ticked list, and the bar can be dismissed per agent in that browser. None of this is reported by the agent's `/api/status` endpoint: that endpoint is recomputed per request from live process state and is unreachable once an agent hibernates, which is exactly when a schedule needs to know, and it would put a fact the platform trusts on disk the agent can rewrite.
- **External Skill** — a skill from another repository, declared by source and name and installed through the same additive apply Skill Sets use ([skills](skills.md#skill-set)): the source must be a Skill Source connected for the owner — a user, system or template source — and an entry it cannot apply is reported with the same closed-set verdict rather than dropped. A kit whose skills come from a source the install does not seed is a catalog quality-bar item, not a platform failure. Skills inside the kit repository are never installed by the platform: the harness discovers them as files when it loads the definition. They may still be *declared* as Bundled Skills, which changes nothing at apply and only makes them visible before create.

## Apply

Apply — the `create` procedure of the starter-kits router, since tRPC reserves `apply` — is **create-only** and a composition of existing rails, compensated rather than transactional:

1. Resolve the kit at the catalog's pin. Use the kit's own image when it brings one, otherwise the Template the user picked; refuse when neither exists.
2. Check every required Connection Requirement against the templates of the connections the user granted; refuse before anything is created.
3. Create the Agent through the plain create — from the kit's image or the picked Template — with the grants, the kit's fixed env, size and hibernation override, the Kit Version stamped as a create-time annotation, the declared share roots when the kit declares a knowledge base, and the kit's `seed` as the workspace seed ([agent-lifecycle](agent-lifecycle.md#create)). The setup page may remove the kit's seed (`skipSeed`): the Agent is then created as if the kit shipped none, and its briefing says so. The cross is offered only for a kit without an `install` command — an install runs from that checkout — and apply refuses the combination before anything is created. A kit with an `install` command queues it as a `workspace-command` event next, ahead of everything below.
4. Create the declared schedules, toggling suggested ones off; bind the Slack conversation if one was given. A failure here deletes the fresh Agent and surfaces the error.
5. Wake the Agent.
6. Install the declared external skills. This step waits for the Agent to be reachable, like every skill install, so a kit with external skills returns once the Agent is up; its verdicts ride back on the apply result, and a failure here is reported, never compensated by deleting the Agent — the requirements that justify a refusal were all checked before create. The apply is recorded in the security log last, once the outcome including the skill verdicts is known.

The catalog has two entry points, answering the placement question in #447 with *both*: a **Starter kits** destination in the rail with the full catalog and setup pages, and a **browse button on Home**, beside the other entry points. It opens the catalog as a modal over the page — the same Browse Kits modal the setup page's Change button opens — and a pick goes straight to that kit's setup. Neither sits behind a flag: kits are how an agent is set up here, so the catalog is part of the product rather than something to opt into. The widget renders nothing when the install has no catalog.

**Kit Onboarding** is the briefing the onboarding event carries — **visible** in the session where the knowledge-base and experiment bootstraps are hidden. Those two send a bare slash command, a mechanical trigger with nothing to read; a kit sends a briefing the user needs, because the agent's first act is to ask them for what only they can supply, and the answers only make sense against what the platform already set up. The prompt is **platform-composed from the kit and the Agent's state, read when the turn is composed** rather than snapshotted at create: the definition repository and the commit it is checked out at, each connection requirement with whether it is required or suggested *and whether it is actually connected right now*, the Agent's real schedules and which are disabled, the bound channel — then "follow `ONBOARDING.md`", or the kit's own `onboarding.prompt` as the instruction. What onboarding asks for is `ONBOARDING.md`'s to say; the platform declares nothing about it. Reading live matters because the user can change any of it between create and the first turn: disable a schedule, drop a connection, or simply never grant a suggested one. A connection the user has since deleted reads as not connected rather than failing the prompt. Every kit ships `ONBOARDING.md` beside `kit.yaml`; the platform has seeded the definition into the work directory before the session opens, so the briefing points at the checkout rather than asking for a clone.

## Invariants

- **Kits are catalog-only platform inputs.** The platform never reads configuration back out of an Agent's own repository or workspace, so an agent committing to either can widen nothing the platform enforces — connections, egress, channels and the Template stay owner-managed platform state.
- **Requirements are checked before create.** A missing required connection is refused with nothing to clean up.
- **Kits are defined in git; the platform stores only their resolution.** The catalog locators are the only configuration, the resolved rows are a cache the refresh job rebuilds from the catalogs, and the Agent's kit stamp is provenance, not a source the platform re-reads.
