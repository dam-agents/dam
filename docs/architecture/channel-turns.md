# Channel turns

Last verified: 2026-09-23

What happens when a channel message becomes an agent turn: the inbound relay from messenger to ACP session, the outbound tools the agent answers with, the liveness watch on a running relay, and the recovery that rescues an undelivered answer. What a channel *is* — bindings, adapters, topology, identity — lives on [channels](channels.md).

## Inbound — channel message to ACP session

```mermaid
sequenceDiagram
  autonumber
  participant U as Channel user
  participant M as Messenger API
  participant W as Worker<br/>(Slack/Telegram)
  participant API as api-server relay
  participant POD as agent pod

  U->>M: post message in thread
  M-->>W: event delivery<br/>(Socket Mode / long-poll)
  W->>W: identity / auth checks
  W->>API: ACP session/list
  API-->>W: sessions + platform meta<br/>(wakes pod if hibernated)
  alt a session's thread key matches
    W->>M: Slack only: read after this Agent's last turn
    M-->>W: messages it has not seen
    W->>API: ACP session/prompt<br/>(resume + catch-up)
  else first message in thread
    W->>API: ACP session/new<br/>(platform meta: type, thread)
    API-->>W: sessionId
    W->>API: ACP session/prompt<br/>(thread history as context)
  end
  API->>POD: relay frames<br/>(wake if hibernated)
  POD->>API: reply / react tool call<br/>(outbound MCP, see below)
  API->>W: reply(threadTs, text) / react
  W->>M: post reply in thread
  M-->>U: reply visible
  Note over POD,W: plain assistant text is not posted;<br/>the agent must call a tool
```

A few observations the diagram glosses over:

- **The gates are the binding check plus the binding owner's Terms-of-Use acceptance** — no sender identity is resolved. Both messengers behave identically here. An unallowed host is refused, not held ([egress](security-and-credentials.md)).
- **An attachment is a picture the agent is shown or a file it is handed**, by what the sender sent, not what the bytes are. Slack only: Telegram drops one at its gateway. A picture becomes prompt content only in a format the harness decodes, the sniffed type outranking the messenger's label. Everything else is written into the agent's workspace and linked by absolute path, as a web-UI upload is, whatever its format. Anything withheld — a refusing messenger, a failed write, a size ceiling — is named to the agent, and on an addressed turn to the sender too.
- **A relayed turn answers its own permission prompts, and it answers them no.** A harness that stops to ask before a sensitive tool call is asking somebody who is not there: the relay holds no verdict of its own, and the conversation's other members are not the binding owner. So the relay refuses and the turn carries on with that one call denied, rather than waiting on an answer that cannot come — the same rule the credentialed-egress gate applies to an unattended turn ([security-and-credentials](security-and-credentials.md)). That holds where the harness offers a way to say no; where it offers only ways to say yes the sole honest answer left is to cancel, which ends the whole turn rather than the one call in it. The relay never picks an approval to keep a turn alive. What an Agent may do on a channel turn is therefore exactly what its session's permission mode lets it do *without* asking, which makes that mode the dial over channel behavior. The platform's own tool surface is kept outside that dial wherever the harness can express it: the Claude Code image pre-approves the two MCP servers the platform injects, so disposing of a turn, reporting an invocation result and reading a knowledge base keep working there in every mode. Reach on those tools is the platform's to enforce (per-Agent endpoint, mesh identity, the binding), never the harness's, so pre-approving them widens nothing. A harness offering no such allowlist has no equivalent, and an asking mode on one denies the reply tool itself: the Agent goes silent holding an answer it had no way to deliver, a refusal it cannot even report, since reporting it is also a tool call. That makes an asking mode unusable for a channel-bound Agent there rather than merely strict, which is a property of the harness and belongs in its own configuration copy. Each refusal is recorded in the security log ([logging](logging.md)), so a turn that quietly did less than it was asked stays diagnosable afterwards.
- **Wake is implicit.** The relay step is the same `ACP relay → wake-if-hibernated → forward` path used by the UI. Channels do not call lifecycle endpoints directly; routing an ACP frame is what wakes the pod ([agent-lifecycle](agent-lifecycle.md), §Wake).
- **Wake failures are surfaced in human terms.** A cold start announces itself to the Slack sender (requester-only notice); a wake that misses its budget while the pods are still progressing posts a still-starting note once and keeps waiting while the cause stays transient, bounded by elapsed time, so a healthy-but-slow start never loses the turn. A hard failure (pod crash, bad image, a wedged gateway, reconcile error) replies with copy derived from the classified wake-failure cause — never the internal error string. The one message passed through verbatim is a refusal to start: the controller's text names what is full and what to stop, which no copy written here could reproduce; a cause the platform is itself repairing still invites a retry. Telegram replies with the same copy on wake failures (no early notice, no extended wait).
- **The agent posts by calling a tool — plain assistant text is never delivered.** A Slack turn's reply reaches the channel only when the agent calls one of its outbound tools (see [Outbound](#outbound--agent-to-channel)), mirroring how Telegram already works. The relay hands the message to the pod and waits for the turn to finish, but the assistant's generated text is discarded — nothing is auto-posted, and an addressed turn that ends having posted nothing is nudged to deliver it (see [the turn watch](#the-turn-watch--liveness-not-duration)). The prompt carries a per-turn contract stating this and naming the thread and triggering message the tools target by default, so the agent replies into the right thread without tracking ids. It also situates the turn: the bot's identity, when the message was sent, which kind of conversation it is, and a permalink where Slack resolves one. A mention or DM turn is marked addressed, and the contract names the ways people reach an agent — the bot's tag, the agent's signed name, and (only where plain messages reach it) the bot name with no tag.
- **The contract speaks for its own message.** A session continued in the UI carries this text with it, so the contract scopes itself to its own message and says what an unframed one means: not from Slack, answered where it arrived, reaching Slack on request ([platform-topology](platform-topology.md), §ui).
- **A working status is the one thing the platform presents on the agent's behalf.** On mention turns a per-turn _presenter_ drives Slack's assistant-status surface — thinking, the current tool as it changes, waking during a cold start — cleared on every turn-exit path. Thought and tool notifications feed it; assistant text is ignored. The status degrades to nothing where the workspace can't show it. Ambient turns present no status — nobody summoned the agent. System notices (wake failures, a still-starting note) are separate direct posts, not agent content.
- **Resume vs. new is decided by the ACP session list.** The binding lives on the session itself: the worker lists an Agent's sessions over ACP and resumes the one whose thread key matches. A resume that fails (PVC lost, session expired) falls back to a fresh session with thread history injected from the messenger API — no regression, just a colder start.
- **A resumed conversation is caught up on what it missed, best-effort (Slack).** A session belongs to one Agent, so it sees a conversation's history only on its first turn there; a mention-only binding is never handed what does not tag it, and an Agent stopped or unreachable is handed nothing at all. A resuming turn therefore also carries what arrived after its own last turn, labelled as above and marked unseen: its own posts stay out, and nothing new means no block. Catch-up looks strictly backward from the turn's own messages — anything sent after them is already queued for a turn of its own and is never presented as missed. The boundary only advances with a delivered turn, and never past the newest message that turn carried by send time — batched or steered into it — whatever order the events arrived in; a read that hit its cap holds it back further still, to the newest message actually read. A failed turn leaves it alone, so the next turn's catch-up recovers everything the failed one held. Both a thread's session and the rolling per-channel read-along session are caught up this way. The boundary is in-process, so a restart or a handover loses it; the Agent's own last post stands in — on the channel session never further back than a rolling recent window — else the window itself: there is always a floor. A capped read says so, and the Agent is told to act only on what is still open. Excluded: Telegram.
- **A conversation answers a burst once, one turn at a time.** People write a thought over several messages, so messages for one conversation gather behind a short quiet period and one turn carries them all. A message arriving while a turn runs is **steered** into it where the harness advertises support for that, so the Agent reads it before calling its reply tool; otherwise it becomes the next turn, never a second turn racing the first. Both the batch and the wait are capped. A message carrying attachments is never steered — they reach the Agent through their own turn — and it holds back what follows, so nothing is reordered. Both messengers share the queue, and so does read-along traffic — but a read-along batch is never steered, since it fans out to one turn per reading Agent and there is no single turn to steer into. The queue is per conversation: the thread where there is one, else the chat on Telegram, or the channel on Slack — narrowed to the sender where the Agent was addressed, so two people raising different things stay separate turns.
- **A session key is adapter-specific.** Slack pairs the conversation with the thread; Telegram uses the conversation (chat plus optional forum topic). Slack's pairing is what isolates an Agent's bindings from each other — a thread id is unique only inside its conversation, so a bare one would cross channels. Nothing in a store guards the key: Slack serializes turns per (Agent, session key) across the session match and the prompt, so concurrent first messages cannot mint duplicate sessions.
- **Injected history says what it is, and it does not say the same thing twice.** Every message the turn itself carries is left out of it, the whole batch where a burst is answered at once, so nothing the Agent is being asked to answer is also quoted back as background. A thread's history and a direct message's are one conversation, framed as the context for the answer. A channel's window is the stream outside threads — several unrelated topics interleaved, each line's send time the boundary — framed as background to read, not answer. Catch-up on a resumed session inverts that deliberately: that block *is* a backlog, and what is still open in it is the Agent's to act on. **A channel window is also incomplete**: the channel read returns only what the channel itself shows, so a reply inside a thread is absent unless it was broadcast — which is how an Agent reads a request its own thread already settled as still open. A line that opened a thread is therefore marked with its reply count, when the thread last moved, and the id that reads it. The marker and its explanation appear only where true — never in a thread's own history, whose replies are already in front of the Agent — and a read-along Agent is told about the multi-topic stream even when its turn carries no block. **Limits**: a thread is surfaced only when its opening message sits in an injected window — reply activity never re-surfaces a parent, the counts are a snapshot from that moment, and a live-fed read-along channel session therefore learns that threads formed only at catch-up.
- **Injected history is attributed per Agent (Slack).** When a fresh session injects thread/channel history, each prior message is labelled by author. Because a workspace's one bot posts for every Agent, a bot message's Slack user id cannot tell Agents apart — so the worker takes the Agent id from each message's [Agent Footer](#the-agent-footer): the reading Agent's own posts are marked as its own, another Agent's are named, and humans keep their Slack id. Names are resolved from those ids rather than read off the footer, so a renamed Agent's older posts carry its **current** name. This lets an Agent reaching into a channel bound to a different Agent stay distinguishable when that Agent later reads the channel. A footer-less bot post is named as the bot itself — unattributable, so never the reader's own.
- **Ambient routing: one session per thread, plus one per channel.** On an ambient binding, a thread reply relays into that thread's own session — the same key a mention there would resume. Top-level messages share a single rolling **ambient session** per channel, so the agent follows the channel rather than starting cold per message. **All** ambient traffic is serialized per session and coalesced under the same rule as addressed traffic (above). A coalesced prompt tags each message with its own ts: a thread batch still answers into its one thread, but a top-level batch has no single triggering message — each batched message registers as its own reply target, and a reply naming none is refused rather than threaded under the newest. When the agent chimes in, the reply threads under the message it answers; the follow-up conversation runs as an ordinary thread session, with history injection carrying context across.
- **Every turn relay is evented.** Both workers announce the finished turn on the in-process bus, naming the messenger, the Agent, and whether it succeeded. It carries no platform identity — channel turns resolve none — so attribution rides the messenger-native id of the sender instead. A failure also carries a low-cardinality failure reason (a wake-failure cause, a turn-watch verdict, or a relay error), which the audit trail and usage records project — so failed turns are diagnosable from the log store after the fact. A delivery nudge announces itself on the same bus rather than amending the turn's own event, so a relay that had to be repaired shows as two: the turn as it first ended, then the nudge and whether it drew an answer. That second one names itself in its reason whichever way it went, so a repaired turn is never mistaken for a plain one. The usage subsystem consumes this for activity tracking ([usage-tracking](usage-tracking.md)).

## The turn watch — liveness, not duration

A relayed turn has **no time limit** — like a session driven from the UI, it runs until the agent is done. While the relay's connection is up it watches for *life*, not length: transport pings guard the socket, and once frames have been silent for the stall-probe window the relay asks agent-runtime whether the session still has a turn running — alive means keep waiting, however long the work takes. The probe window is floor-bounded by the egress-approval hold at config load (raising a lower setting with a startup warning), so a turn silently waiting on an approval is never probed early. The relay abandons a turn on exactly two verdicts — the connection is lost, or the runtime reports the turn gone — and abandoning the relay never touches the work: the harness keeps running detached, and its late reply still lands through the lingering turn record.

An addressed turn that fails is answered in plain language keyed to what happened, never a raw error — and answered not at all where the thread already carries the agent's own post or a deliberate decline or hand-off. The failure reason still rides the turn event either way.

An abandoned turn is handed to the **recovery watch**, which polls the session's run status for as long as the runtime reports it alive. The work counts as over only on a positive signal: the runtime says the turn ended or that its own boot recovery gave the turn up, or the platform reports the pod gone — which under a running turn means the turn is over, because the idle checker never hibernates a pod holding one. A failed status read is unknown and simply polled again; only a session that never shows life runs out the watch's rolling window. Once the work is over, delivery is judged by **how it ended, never by timing**: a turn that ended in-process made its full disposition and is nudged only when it posted and declined nothing — the same verdict a never-abandoned turn gets — while an interrupted turn never completed, so any interim post was a partial and it is nudged unless its silence was deliberate. The nudge resumes the session with an undelivered-turn notice and the agent posts its own late answer, or declines — which keeps the invariant that the platform never authors assistant text; the nudge and boot recovery's interruption resume ([agent-lifecycle](agent-lifecycle.md)) are the only platform-authored prompts an agent ever sees. A later turn answering on the same session dismisses the watch, so a person who re-asked never gets two answers. The watch runs on Slack's addressed turns only: an ambient turn is never nudged — nobody summoned the agent — and Telegram gets the failure copy alone.

What counts as answered spans everything the turn gathered, not the batch it opened with: a message steered into a running turn takes its own place in that turn, and the agent's one reply may land against it rather than the message that started things. Judging on the opening batch alone reads an answered turn as silent — and then repairs it, which is how a person ends up sent the same answer twice.

A turn that never lost its relay needs no watch, and is judged the moment it ends. An addressed Slack turn that finishes having posted nothing, declined nothing and handed nothing on has left its answer undelivered — the agent wrote it as ordinary text, and the relay discards that — so it goes to the same watch with its ending already known: no poll, the verdict runs at once, and the recovery is the one the watch would have reached anyway. This is the common case nothing else catches — nothing failed, so nothing is abandoned; the person simply waits on an answer that was written and never sent. One owner decides both, which is what stops the two paths drifting into two different ideas of what "answered" means. The notice tells the agent to post the answer *as* the answer rather than as a correction — nobody saw a failure, so apologising for a delay they never noticed explains the platform instead of replying to them. After an abandoned turn the notice says the opposite, because there the failure copy is already on screen above the agent's own post. Both paths nudge at most **once**: an agent still silent afterwards is left alone, because a second notice only repeats the first, and a nudge never authors anything itself — what reaches the channel is the agent's own post, or nothing. A nudge waiting on its turn holds only what it needs to post — the thread and what the turn has disposed so far — never the message's downloaded images or files, since a watch can outlast the turn by hours. A replica standing down cancels every watch and waits, for a bounded time, for any nudge already running — one still waiting to wake the agent stands down on its own, one already prompting it finishes — and logs whether they drained or how many were abandoned at the limit. From then on it registers no new watch, so a turn that settles during shutdown is never nudged from a replica that has stood down.

## Outbound — agent to channel

Outbound is initiated by the agent process. The harness calls a tool on the api-server's per-Agent MCP endpoint, the endpoint authenticates the call, and the channel manager routes the message back through the right worker.

What the agent sees:

- **Cross-channel tools.** `describe_channel` reports the chats an Agent can reach; `send_channel_message` makes a **new top-level post** — for proactive or cross-channel messages, and on Slack never a turn reply, which `reply` owns. Telegram has no thread to reply into, so there it is also how a turn is answered. Where a target is ambiguous the worker refuses and names the candidates rather than picking one.
- **The agent meets people as ids, and resolves them itself.** A messenger names a person only by their user id — in speaker labels, injected history, and mentions inside message text — so `describe_channel_users` turns ids into people, as far as the workspace discloses. The lookup posts nothing, is gated by the binding, and is logged by the ids asked about, never the profiles. Ids travel inbound only: the turn contract forbids writing a bare id back into a message — nobody in the channel can read one — and points the Agent at a Slack mention or the name it resolved instead. That holds whether or not the lookup is available. Slack-only: Telegram has no workspace directory.
- **A thread the Agent is not inside is read with `read_thread`.** It returns the thread labelled exactly as injected history is, and reads the **end** of a long thread, not its opening — the question is what a conversation concluded. Its reach is **what the platform offered**: a thread id resolves only against threads recently marked in that Agent's own injected history, which also settles which conversation the id lives in, and that conversation must still be bound. It is the one outbound tool that returns message bodies, so any wider reach would read every room the bot sits in; a forged or found id resolves to nothing, and offers are in-process and age out (48h), so a restart degrades to a refusal, never a wrong read. The scope it needs is already required, so it never drops out per workspace. The log records what was asked and how much came back, never the messages. Slack only.
- **Reactions are otherwise invisible; `describe_message_reactions` is how an agent asks.** Never cached, unlike the user directory: a tally is live state, and the current count is the point of asking. Gated by the binding; the log records the message and tally, never who reacted. Slack only.
- **Slack turn tools** — `reply`, `react`, and `hand_off_to_agent` — are how an Agent disposes of the turn it is handling. A reply may additionally surface in the channel (Slack's native "also send to channel"), off by default, and may carry one file, as `send_channel_message` can. A thread-triggered turn is never nudged towards it: the thread is where the answer belongs, and surfacing it to the channel takes an explicit ask. The one turn still nudged is a coalesced batch of top-level messages, which has no thread the channel is already watching. A single Agent pod multiplexes every thread over one harness process and one outbound MCP identity, so a call that does not name its target carries nothing to tell concurrent turns apart: where the candidates disagree the worker **refuses and asks for the injected id** rather than guess — posting one thread's reply into another is the failure worth preventing. A call targeting a turn posts into that turn's own conversation, not whatever the Agent is bound to at call time, so a mid-turn rebind cannot redirect an in-flight reply.
- **An Agent can hand its turn to a peer.** In a conversation holding several Agents, `hand_off_to_agent` gives the message to another Agent connected there — the default Agent acting as a router, or an Agent that was named but is the wrong one. The receiving Agent picks it up as its own turn and answers in the thread itself; the handing Agent posts nothing and its turn ends, counted as deliberately disposed of rather than unanswered. A handed-on message **cannot be handed on again**, which is what stops a message circling. The hand-off is refused when the named Agent is not connected there, is the caller itself, or cannot take turns yet; attribution stays with the original human sender, with the hop recorded.
- **`no_reply_needed` is cross-channel.** Both messengers instruct the agent to call it to end a turn deliberately silent, rather than leaving undelivered text. It posts nothing and touches no channel, but it does mark the turn declined — which keeps a sanctioned silence out of the unanswered-turn signal.
- **Slack reach is the bot's own membership.** A bound Agent may post beyond its bound conversations: any channel that workspace's bot belongs to is a valid target, and a Slack user id opens a DM. Membership is verified at send time; a bound conversation short-circuits every check, so it keeps working regardless of app scopes. Every outbound post is made by the bot and footed with an [Agent Footer](#the-agent-footer). The workspace is the reach boundary, granted scopes the ceiling. The binding governs who may drive the Agent inbound, not what the Agent does outbound. Telegram has no analogue: its outbound targets stay the conversations bound to the Agent.
- **Tools are always registered.** Calls are rejected at invocation time when no channel is connected for the Agent — no dynamic tool list, no per-session toggle. `describe_channel_users` and `describe_message_reactions` stay registered too, and report the scope their workspace withheld (see [Slack scopes: required vs. optional](channels.md#slack-scopes-required-vs-optional)). Workspaces grant differently, so a tool list that is per-Agent cannot answer for all of them: the strategy is picked by whether a partial answer is possible, and across workspaces one always is.
- **Bidirectional channel.** If a channel is connected to an Agent, every session on that Agent can post — interactive and scheduled alike. There is no per-session outbound flag.

Why the dedicated MCP endpoint: it is the only api-server port the agent's NetworkPolicy admits, and it is per-Agent by path with the mesh admitting each Agent's identity to its own path alone — so what stops a compromised harness posting as another Agent is that boundary, not the channel layer ([platform-topology](platform-topology.md), [security-and-credentials](security-and-credentials.md)). What channels adds is directness: the endpoint dispatches into the same posting path the workers use internally, with no agent-runtime round-trip and no second relay hop.

### The Agent Footer

Every post the bot makes is footed with an **Agent Footer**: a context block linking to the posting Agent's [Public Agent Page](public-agent-page.md), carrying the Agent id and — on a turn's reply — the session it ran on. Its owner picks that conversation up in the UI, where only they may open it ([platform-topology](platform-topology.md), §ui); everyone else lands on a page naming the Agent rather than a dead end.

The footer has two separable parts and **only one is a contract**. The **Agent id in the URL is the wire format** — parsing it back out is how the api-server recovers the author when a post later surfaces in another Agent's injected history (see [Inbound](#inbound--channel-message-to-acp-session)). The **link label is presentation**: nothing parses it, so product rewords it freely — today the posting Agent's name and the brand, which is what tells two Agents in one conversation apart.

Keeping those apart is an **invariant**, not tidiness. Attribution used to read the Agent's name out of the label, so rewording it into a brand line silently unnamed every Agent in injected history — a copy change breaking a runtime feature, with nothing failing anywhere. Attribution reads the id and resolves a name from it, which is also why the parser still accepts the footer's older link forms (the authenticated chat route and its retired predecessor): history predating the change stays attributable.

### Threading model

Outbound posts are **fire-and-forget at the thread level**. The agent posts a top-level message; the worker stores no thread-to-session mapping for proactive posts. If a user replies to the resulting thread, the inbound path treats it as a new mention — a fresh session. Continuity from the originating session does not carry over. This is the deliberate trade-off: keep outbound simple and stateless at the cost of session bridging on Slack-side replies.

The two messengers diverge slightly on what a top-level post means:

- **Slack:** the worker posts outside any thread, producing a new top-level message. A reply to it is routed by the _reply conversation's own_ bindings like any inbound message — so it reaches whoever that conversation's routing resolves, which need not be the Agent that posted, and nobody where none is connected. An Agent-initiated DM lands in the person's DM regardless of any binding but does not itself bind it: for their replies to reach the Agent, the DM must be connected like any other conversation.
- **Telegram:** there is no thread primitive in DMs and only weak threading in groups. The worker posts to the chat id; if the agent's prompt was triggered by a previous message in the same chat, that chat is still the conversation.
