# Harness configuration

Last verified: 2026-10-09

## Overview

How an owner's mode and config-defaults choices for each harness an agent carries — or a driver's, for an agent it spawns — reach that harness's own configuration file, where the model list behind those choices comes from, and what the Config panel shows while the agent is stopped.

The choices travel as a `harness-config` Event over the [runtime channel](runtime-delivery.md) — that page owns delivery and capability gating; this one owns what the event means and everything built on it.

These are each harness's defaults: writing them recycles only the [Harness Leases](agent-lifecycle.md#session-inside-the-pod) of that harness. The model is not among them: each session picks its harness, provider and model, so the Config panel shows the settings of every carried harness and no model setting. Every harness gets its model as a lease's environment, which its scripts honour over the config file and a provider pin; a session's model is never switched inside a live harness, because a resumed session would fall back to the file's default. The runtime advertises its default harness and, per carried harness, the catalog. The model list a session or a [schedule](schedules.md#session-model) picks from is asked per harness and provider over the runtime's tRPC, without spawning anything — the discovered one where the provider lists its own. The session picker offers named models, not a generic default-model choice. It shows loading, unavailable and empty listings explicitly, with a retry for failed discovery; a failed listing never falls back to the harness's static catalog. The catalog remains usable where discovery is not configured.

## Provider compatibility

Provider compatibility follows the configured harness catalog, shared by the settings view and session selection. It also follows the [Connection](connections.md)'s credential mode: an Anthropic API key works with Claude Code and Pi, but a subscription OAuth Connection is offered only to Claude Code. Automatic provider selection and scheduled or channel-driven turns apply the same restriction. A provider speaking another harness's API dialect is not enough: the Connection must also supply that harness's authentication and endpoint configuration.

## The event

`harness-config` is the mode/config-defaults mechanism: a user action in the Config panel fires one event, naming the harness it is for — the api-server refuses one the agent's runtime does not report carrying, and an event naming none means the default harness — and the agent-runtime writes the mapped keys into that harness's own config file once, and — like `workspace-seed` — never re-asserts, so the file stays the user's to edit (a hand-edit via the Files panel or SSH is never reconciled away). Because a harness reads that file only when it spawns, a write is followed by a recycle: idle, the process goes at once; mid-turn, after the work drains, on the same deferral the env rail uses, which a kept [Harness Task](agent-processes.md#reported-background-work) holds back until it ends. Without it a declared value would sit unread until something else happened to restart the harness, which is the shape of a setting that silently does nothing. A spawn is the second producer: a driver may name its child's choices, and the platform queues them ahead of the child's first turn, so that turn already runs on them. No person acts there, so it records neither an activity nor a declared snapshot. A write that fails is reported back rather than only logged in the pod, and for a spawned child that report fails the spawn, since the turn behind it would otherwise run on the default. The Config panel is driven entirely outbound, not over an ACP session: every carried harness's manifest declares its own `harness-config` driver entry, the runtime running one per harness, carrying both the field → file-keyPath mapping — a config option may name several key paths, which one choice writes and unsets together and the first of which is read back as its value, so a harness keeping one setting under two keys (Claude Code's prompt-cache TTL for the conversation and for its subagents) still offers one choice — and an option **catalog** (the available model/mode/config choices and their per-model validity), and the agent advertises that catalog on `hello` (alongside a `harnessConfig` capability flag) for the api-server to serve to the UI; the *current* values are read back live from the config file via the agent-runtime `harnessConfig.current` query. A manifest may instead declare a `modelDiscovery` source, in which case that same read fills the model list live from the provider rather than from the static catalog — or, for a source marked as extending it, after the catalog's own models, for a harness whose catalog means something on every provider. A source is declared against the env rail: it names, in priority order, the variables a granted connection materializes the provider's base URL into, so *which* endpoint is asked follows from what the agent was granted, and it says which model-listing dialect that provider speaks. The order carries weight because an agent can hold several connections at once and the rail settles a name claimed twice by an order nobody chose, so a connection that redirects the harness and one that merely supplies the harness's own endpoint contribute different variables and let the source rank them. To be usable a provider has to answer such a listing over the agent's normal egress and let a conversational model be told apart from the rest of what it fronts; nothing else about it matters, and because the request leaves the pod through the credential-injecting gateway like any other, discovery authenticates with the injected credential rather than one the agent holds. The source names the variables that hold the connection's credential placeholder, and the listing carries it as a harness request would: a gateway that injects only addressed requests learns the connection from it, and one that injects every request replaces it. Once the env rail has materialized, no connection supplying a URL means the agent has no provider to list, so the read reports no list at all and one an earlier provider established is cleared rather than left offering models the agent can no longer reach; before that first materialization a missing URL says nothing about the grant. A source may also name a second listing on the same endpoint, asked only when the provider refuses the first: a LiteLLM key can be barred from the model-information route yet allowed the OpenAI model list, which says nothing of what a model is for, so there only the name keeps an embedding model out. A provider that refuses every listing or cannot be reached and a listing with no conversational model in it are one outcome — *unavailable* — which leaves whatever list was last established in place and never fails the read; the first read of a pod's life pays DNS and a TLS handshake before any of that, so it is retried once rather than being written off on a merely slow cold path. Which choices a harness offers is its catalog's to say: Codex's offers no mode, because its image runs it never asking for approval, so there is no permission mode to pick and nothing for a [channel turn](channel-turns.md) to refuse.

## Model discovery and the seeded model

A discovery source is also what lets a **seeded model** exist, and it is the one write to that file no user action is behind. A harness pointed at somebody else's provider cannot rely on its own built-in default: the model it would name need not exist upstream, and a listing that does not know it refuses the turn outright rather than substituting anything — so an agent nobody has configured yet fails its very first prompt. The seed closes that: with nothing set and nothing pinned on the provider, agent-runtime writes the first of the discovered names — the list is ordered, so the pick is stable rather than whatever the provider happened to return first — before the default lease's harness spawns: at boot, and again before the spawn that follows an env change, since a provider switch reaches the pod as one. The boot gate holds early callers until it lands under a ceiling of its own, and a listing that cannot be reached is asked again for a while first, because the gateway fronting a newly granted provider is still rolling when its env lands. It never speaks over a value somebody chose that the provider lists: a hand-edit the listing knows stays, and a session that picks its model never needs the seed, and with nothing in the file a provider pin the listing knows is the default. A model the listing does not know — in the file, or pinned by a connection whose catalogue has moved on — is not left to fail every turn: a file model is cleared when the provider lists the pin, and otherwise the first listed name takes its place, which is how a model chosen on one provider does not outlive a switch to another and a retired pin does not stop an agent. Between a pin and the file, the file wins: a connection's model pin is only a default, checked against the live listing each time it would apply, and a model in the file that the provider offers outranks it, so a choice is never silently overridden by the connection it rides on. Whether a source justifies it follows from *which* variable supplied the URL, which is why the manifest marks the redirecting ones apart from those that merely carry the harness's own endpoint: on its own provider the harness's default is the better answer and stays untouched. An unavailable listing seeds nothing, so a harness whose provider cannot be reached keeps the behavior it had — the seed can pick a model, not invent one. Only harnesses whose manifest declares the `harness-config` driver honor the event and advertise the capability that gates the UI section; a spawn that names choices for a child without it, or names a setting the child's catalog does not offer, fails rather than letting the child run on its default.

Bedrock is the third dialect, after the OpenAI model list and LiteLLM's model info. The [AWS Bedrock](connections.md#app-preset-aws-bedrock) Connection names the region's control-plane endpoint, and Pi's manifest declares it as a source ahead of its OpenAI one, speaking Bedrock's inference-profile listing — the profiles that can be invoked from that region, each carrying a region prefix a bare model ID lacks, which is why a typed ID is the wrong unit to offer. Models Bedrock also serves on demand under their bare ID are not in that listing, so they are not offered either; the Anthropic models a coding harness runs on are reachable only through a profile. A manifest lists its sources in priority order and the first whose variable is set answers, so one harness fronts several providers' dialects without a static catalog. The seed and the provider pin behave exactly as for an OpenAI-shaped provider. What no listing can say is whether the account has been granted a model: that is learned at the first call, as an error the turn reports. Claude Code's catalog is model tiers, which Claude Code itself resolves to the region's Bedrock profiles ([connections](connections.md#app-preset-aws-bedrock)), so its source asks only the LiteLLM-shaped endpoint a connection points it at, and extends the tiers rather than replacing them. There its in-pod model gateway defaults every tier to the newest model the provider has for it, which on a provider that serves no Claude model is one model for all of them unless the Connection pins the slots; the provider's other models are reachable only by name, so the panel lists them after the tiers, under the lowercased, `claude/`-prefixed names the gateway publishes to Claude Code itself, so a choice made in the panel and one made in Claude Code's own model picker are the same value. Nothing is seeded: the tiers already resolve on any provider.

CurveBender pins Claude Code's Sonnet slot to its non-reasoning Nemotron model for the auto-permission classifier, and every work slot and the default conversation to GLM. It also turns off the server-side auto-mode check: GLM cannot answer the classifier's non-thinking request within its deadline, so the model pin and that flag are needed together. The Connection disables unsupported tool search and declares the deployment's supported context window. These are provider-scoped defaults, not a change of permission mode; a session's model and explicit agent settings still take precedence. Its model listing remains the upstream catalog, so Nemotron can still be selected explicitly but is not a work-model default.

The runtime also reports the harness's **default**, what a session runs on when the config file names no model: a model the provider pins through its environment, otherwise a manifest-declared value that selects the harness's built-in default for one session. Only a harness that can switch a session's model reports one. A [schedule](schedules.md#session-model) with no model runs on it on a runtime with one harness process; where each session picks its harness, it runs on the pair a person last picked.

## Snapshots

Because the live read needs a running pod, the platform also keeps a **snapshot** of these values, so the Config panel renders the last known configuration while the agent is stopped. An apply records what it *declared*; a snapshot is display state and is never re-asserted onto the harness, so the harness's own file stays authoritative and the live read wins whenever the agent is up. A snapshot always carries the moment it was captured, and whether a pod has confirmed it or it is merely what an apply asserted — the distinction matters precisely because the event never re-asserts, so a hand-edit can move the file out from under a declared value. Snapshots are kept per harness, and the pod reports each carried harness's values at two points, and the split is forced: on `hello` it reports the files' values alone, since a clean boot with nothing pending never applies and a hand-edit would otherwise go unseen for that whole run; the apply reply reports those plus the discovered model list, which can only be resolved once the env driver has materialized the provider's base URL. A report omits the model list when it could not be resolved, so a failed read never erases one an earlier read established; a harness with no discovery source, or no provider for one, records that fact instead.
