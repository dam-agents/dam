# Schedules

Last verified: 2026-10-07

## Overview

A **Schedule** is a task attached to an Agent that fires on its own: a cron or RRULE recurrence — or a single moment, a **one-time schedule** — a task prompt, and for a recurrence an optional **Precheck** that decides each occurrence before any model is woken. Schedules are the one way work starts on an Agent with nobody watching, which is why they own three things no other caller needs — arming the next occurrence durably, waking a hibernated Agent to receive a fire, and deciding whether a fire is worth a turn at all.

The subsystem straddles two components. The api-server owns the schedule rows, the queue that arms them, and the decision to fire; agent-runtime owns what a fire *becomes* — the Session it opens, the Precheck it runs first, and the verdict it reports back. Everything between the two — the outbox, the delivery worker, the event's TTL — belongs to [runtime delivery](runtime-delivery.md) and is not restated here. Waking and hibernating the Agent a fire lands on belong to [agent-lifecycle](agent-lifecycle.md).

## Fire

Schedules are Postgres rows owned by the api-server, each armed as a delayed job on a Redis-backed queue — one pending job per schedule, re-armed after every fire. Fires are idempotent per occurrence, so at-least-once delivery cannot run one twice and a boot cannot swallow one that is due; a periodic reconcile re-arms any schedule whose queue job vanished. The next occurrence is computed from the schedule's cron or RRULE expression in its timezone, skipping any occurrence that falls inside an enabled quiet-hours window. Suppressed fires are dropped, not deferred — quiet hours mean "skip these," not "queue for later" — and a schedule whose every occurrence is quiet is rejected at save time. Every RRULE counts its steps from one fixed start — midnight on 1 January 2001 in the schedule's timezone, a Monday and the first of a month — so its occurrences never depend on when they are computed and stay put across restarts and re-arms: an unanchored rule defaults to midnight, weekly to Monday, monthly to the 1st. `COUNT` is rejected, because counted from that start it would be spent, and so is `FREQ=SECONDLY`, because schedules fire at minute granularity. A rule with no future occurrence is rejected at save time; the occurrence search runs on the api-server's event loop, so every search is capped in the periods and candidate times it may examine, and a rule that can never fire answers at once instead of blocking it. An occurrence inside quiet hours resumes the search at the end of that window, and a rule still quiet after 64 windows counts as covered. Rules longer than 1,000 characters or with an `INTERVAL` above 10,000 are rejected. A local time erased by the spring-forward jump is skipped, as RFC 5545 requires. An enabled schedule with no next run shows why — a refused rule, one that never fires or has run out, or quiet hours that cover every remaining occurrence — worked out when the schedule is read, so it clears the moment an edit re-arms it.

When a fire is due:

1. The api-server inserts a `trigger` event into the Agent's runtime outbox in the same transaction that bumps the Agent's version, then signals the delivery worker. The fire is durable from this point; a recurring schedule re-arms once the commit succeeds; a failed commit is retried by the queue, then by the reconcile.
2. The api-server pokes the Agent's activity annotation so the reconciler scales a hibernated Agent up. The poke never waits on readiness; a poke that errors is recorded as a failed fire on the schedule's status (a [one-time schedule](#one-time-schedules) excepted), but the committed event still delivers if the Agent comes `Ready` within its TTL.
3. The delivery worker pushes the event over the runtime channel's `applyState` — only once the Agent is `Ready`. A waking Agent picks pending events up on its boot-time `hello` catch-up. Every event carries a TTL, so an Agent that stays down through several occurrences (error state, failed poke) doesn't replay a backlog of stale fires when it eventually wakes. Outbox mechanics — versioning, the sweep, expiry — are owned by [runtime delivery](runtime-delivery.md#event-lifecycle).
4. agent-runtime's trigger handler opens an ACP session against the harness over an in-process channel and submits the task as a prompt. The turn itself runs asynchronously in the harness, and the event settles once the prompt is submitted. **A fire carrying a Precheck settles earlier — the moment the handler accepts it** — and decides afterwards: the handler runs inside the delivery call, and a check may run for minutes ([runtime delivery](runtime-delivery.md#event-lifecycle)).

A fire on an Agent created from a [starter kit](starter-kits.md#concepts) whose onboarding is still pending is **held** before step 1: no event is inserted, the next occurrence is computed and armed as usual, and the schedule's last result reads `held: onboarding not complete`, which the schedules page shows as held rather than failed. The hold reads the Agent's onboarding annotation and lifts the moment the mark lands. A fire on an Agent a [runtime migration](vm-runner.md#runtime-migration) holds down — from the container's stop until the machine has booted from the copy, or after a failure that came after the stop — is held the same way, reading `held: moving to the new runtime`, since the fire could only wait out the wake.

An event that is never delivered stays pending in Postgres and is redelivered until it settles or expires, and the agent keeps a last-fire timestamp per schedule on the PVC, so a redelivered or superseded fire never runs twice. That safety net ends where a fire is settled. For an ordinary fire it covers everything up to the prompt; for a prechecked one it stops at acceptance, so a check that never finishes reaches the pod log and nothing else, while a session that then fails to open is reported as a failed run with its reason. Losing an occurrence that way is the price of not holding the channel open, and for a recurring check the next occurrence pays it back.

## One-time schedules

A task meant to happen once — a check-back, a retry after a transient failure, a hand-off to a session of its own — is a Schedule whose recurrence is a single moment, held in the timezone it was given in. It is a Schedule rather than a concept of its own because it needs exactly what a recurring fire needs: an arm that survives a restart, a wake for a hibernated Agent, and the outbox rail. Handing over a task *now* is the same thing with the moment omitted; it fires at creation, so everything that ran unattended is listed in one place whether a user or the agent started it. The moment is always absolute — a relative delay is not accepted, and the resolved instant is echoed back to the caller, which is how an agent that miscounted the current time finds out.

What a single occurrence changes follows from it having **no next occurrence to make up for a lost one**:

- **It never re-arms.** Completion is derived from the row — it fired and has no next run — rather than stored, so it cannot disagree with the fire that produced it. A completed one leaves the list of what will still happen and stays as history beside the Session it opened, then is pruned 30 days after it fired, a failed fire included. Cancelling is deleting; it can be edited only until it fires; deleting one already on its way does not recall the event.
- **Its result is recorded by delivery, not by commit.** A recurring fire writes its result when the event commits, and a fire lost after that is paid back by the next one. A one-time fire has no next one, so it writes *delivering* in the transaction that commits its event — a settle can never land before it — and reads it until its event settles on the pod (then *success*) or expires undelivered (then *missed*). A wake that fails after that commit leaves it *delivering* rather than recording the failure, since the event is already on its way; the fire's retry finds it committed and only pokes the Agent again. Both transitions come from runtime delivery's per-kind listeners, notified on the api-server once the settle or the drop has committed — no report from the pod, so a runtime too old to know the kind still resolves.
- **Its delivery window is a day, not an hour.** The event expires 24 hours after the moment, and a queue job that runs late inside that window still fires — an Agent in error state or out of budget for a while still gets the task, where a recurring fire would rather skip to the next occurrence. One whose window passed before it could be fired at all is recorded *missed* by the reconcile.
- **Nothing may skip it.** It takes no Precheck, since a decline would mean *never* rather than *not this time*, and no quiet hours, since its moment was chosen deliberately. Neither the onboarding hold nor the runtime-migration hold applies — a hold guards a cadence, and skipping a single occurrence would lose the task outright; during a migration its event simply waits out the move inside its delivery window. A hard stop is overridden exactly as a recurring fire overrides it.
- **It opens a fresh Session** unless tied to the one that scheduled it (below), typed as a one-time schedule's so the surfaces group it with scheduled work. That session can run on a **model of its own** rather than the default — a routine check-back on a cheap model, a hard one-off on a strong one — where the harness can switch a session's model ([harness-config](harness-config.md)); the choice is refused at creation where it cannot, and a harness that still refuses the switch when the task fires fails the task with its reason rather than running it on a model nobody chose. A task that continues its scheduling session keeps that session's model.

An agent may also tie one to **the session that scheduled it**: *continue* makes the task a new turn in that session when it is due, so a check-back keeps the context it was asked in; *report* runs it in a fresh session and, when that turn ends, hands its text back to the scheduling session as a new turn. Either way the scheduling session must be known for certain, and the platform tool has no session of its own — the MCP endpoint is one per agent. So agent-runtime gives every session a reference of its own and hands the harness, for each session it opens or loads, its own copy of the platform MCP entry carrying that reference; the tool records it, and the pod resolves it back when the fire lands. A harness that does not honour a per-session entry sends no reference, and the tool refuses to tie the task to a session rather than guess. The turn that lands in the scheduling session runs **unattended**, as a scheduled fire does, even in a person's chat with no tab open — a permission request in it expires the way a detached run's does. If that session is gone by then, *continue* runs the task in a fresh session instead, so it is not lost; *report* drops the result, since there is nobody left to tell.

An agent creates one through a platform tool of its own — kept apart from the recurring one so a model reaching for "once" is not steered through recurrence and Precheck options that do not apply. Since an agent may create one from any Session, a scheduled one included (a retry, the next check-back), a buggy task could schedule itself without end; agent-created one-time schedules are therefore bounded by how many may wait at once and how many may be created in an hour, both deployment settings. Users are not bound by them. A starter kit cannot declare one: an absolute moment means nothing in a kit applied at any time.

## Precheck

A schedule carries an optional shell command that decides its own fires. Most fires of a periodic check — "did a new PR land?", "is the queue backing up?" — find nothing to do, and reaching that answer through a model is the most expensive way to ask a question a timestamp comparison could settle. The Precheck moves the question out of the turn.

It runs in the agent pod, in the workspace directory, under `bash -lc` with the runtime process's own environment — so `HTTPS_PROXY` still points at the paired gateway and a check may reach GitHub or an API with the same injected credentials the agent gets ([security-and-credentials](security-and-credentials.md)). Running it there is the point: the inputs a real check needs — the workspace, the checkout, credentialed network access — are already present, with no new plumbing to feed them anywhere else. The schedule's id, the occurrence being decided, and the time of the last fire that actually started a run arrive as environment variables, so "anything new since last time?" needs no bookkeeping of its own.

The exit code is the verdict, split the way `grep` splits it: `0` allows the run, `1` declines this occurrence, and every other way the command can end — a higher code, the two-minute deadline, a command that will not spawn — means the Precheck itself broke. A broken Precheck **allows** the run and records the reason, because an optimization that breaks should degrade to the unoptimized behaviour rather than silently stop the work; the opposite default would let one typo exiting `127` silence a schedule for weeks while looking exactly like "nothing changed". A runtime image too old to know the field ignores it and runs, which is the same fail-open. Whatever the command prints on stdout is appended to the task prompt (byte-capped), so the expensive turn does not re-derive what the cheap check just found; stderr does not, except that a broken Precheck's recorded reason carries the tail of it — so the reason reaches the owner's panel and the CLI too, and a check that prints secrets to stderr will show them there. A broken Precheck still contributes that block, carrying what it managed to print marked as unverified, or saying there is none — a task written as "process the items listed below" must never be followed by nothing, or the run acts on a reference it cannot resolve.

Only the pod knows the verdict, so it reports each one back over the runtime channel's generic **event report**, naming the fire by its own event id ([runtime delivery](runtime-delivery.md#event-report--agent--api-server)); the api-server checks that the event belongs to the calling Agent, routes on its kind, and records the verdict on the schedule. The Precheck does not hold the fire's delivery open while it runs — the trigger settles when the pod accepts it, or a two-minute check would stop every other change reaching that Agent. **A schedule with a Precheck records its outcome only once the verdict exists**: the fire itself arms the next occurrence and nothing else, and the report that follows either stamps the last-run pair (allowed, and a broken Precheck that ran anyway) or counts a **declined fire** (`declined`). The decline count is *since the last run*, not a lifetime total — a run resets it — so what the panel shows is how many fires the Precheck has saved since work last actually happened, which is the number that says whether the check is still finding anything (an [on-demand run](#on-demand-run) the Precheck declines counts here too, which is why the unit is fires rather than occurrences). That is what keeps the three states apart in the row the user reads, and it is what makes the last-run stamp mean *the last fire that actually ran* — the meaning the Precheck's own environment depends on. A schedule with no Precheck is unchanged: nothing will report, so the fire records its own delivery as before. The consequence for a runtime image too old to know the field is cosmetic and self-correcting — it runs the task but never reports, so the panel keeps showing the previous run until the image catches up.

A broken Precheck is recorded beside the run it allowed and counted with it. Two things clear that record — the next verdict that isn't a failure, and **editing or removing the Precheck**, since an error recorded against one command says nothing about another. A third case is not cleared but **dropped**: a verdict that describes a Precheck the schedule no longer runs. The check is detached, so an owner can swap the command while one is in flight; writing that verdict would attribute it to a command that never produced it, and clearing on it would wipe what the new command had already recorded. The fire's payload carries the command that ran, which is what lets the report be matched to it.

A report can also simply never arrive — the pod can die mid-check. Then the fire leaves no record at all: the last-run stamp keeps its earlier value, so the next Precheck is told work happened longer ago than it did. The direction is deliberate. An older stamp makes a check find *more* than it should and run again, where a newer one would make it skip an interval's work silently, and the next report that lands corrects it. Its count is consecutive — since the script last ran and returned a verdict at all, allow or decline alike — because a run cannot clear it the way a run clears the decline count: a broken Precheck is what let that run happen, so counting from the last run would read *one* forever and never say that a check has been failing all week. Every report also announces the schedule as changed, so an open UI re-reads rather than waiting for an incidental refresh — which is what puts a broken Precheck in front of its owner on the home surface instead of only in the schedule's own panel.

The declined report also undoes the fire's own cost. The poke in step 2 stamps `last-activity`, which is what keeps a woken Agent from hibernating; a Precheck firing more often than the idle timeout would therefore hold its Agent awake permanently and spend more compute than the turns it saved. So the api-server stashes the stamp it wrote — keyed by occurrence, on a short expiry of its own, and consumed by the first report that claims it — and on a declined report restores the value that preceded it, compare-and-restore against its own stamp, the same shape the [pause flow](agent-lifecycle.md#hibernate) uses, so activity that arrived during the check keeps the Agent warm. What it does not undo is the cleared hard stop: a fire overrides a stop by design, and a declined one leaves the Agent started rather than racing a user who may have started it by hand meanwhile.

The honest limit: this keeps the prompt, the context and the cache out of a declined path, but the Agent still wakes to run the check. Deciding without waking it at all would mean running user code with credentials outside today's boundary, and is not attempted here.

## Session continuity

The session model differs by schedule mode (a one-time schedule is fresh, or lands in the session that scheduled it):

- **Fresh schedule** — every fire creates a new session via `session/new`. The schedule accumulates a list of sessions over time, browseable under the schedules tab.
- **Continuous schedule** — the first fire creates a session via `session/new`; every subsequent fire calls `session/resume` against the same session id. One schedule, one session, history retained across fires.

The schedule↔session link is agent-owned: schedule sessions are typed (`schedule_cron`, or `schedule_once` for a one-time schedule) through ACP session metadata, and the continuous binding is a per-schedule entry in a state file on the PVC. Resetting a continuous schedule rides the same outbox rail as fires — a `schedule-reset` event clears the binding on delivery, so the next fire starts fresh. Unlike a fire, a reset does not poke the Agent awake: one that stays hibernated past the event's TTL expires undelivered, and the next fire resumes the old session. Within a continuous schedule fires serialize naturally — each resumes the same session, prompts queuing at the runtime — while fresh fires each open their own session and may run concurrently.

## Session model

A schedule, recurring or [one-time](#one-time-schedules), can name the model its sessions run on, so a frequent routine check runs on a cheap model and a demanding one on a strong model, without touching the Agent's own model. It can only where the harness declares it can switch one session's model ([harness configuration](harness-config.md)): a model is refused when the schedule is saved on any other harness, and an unknown name is refused against the same model list the Config panel offers. The Agent's model is agent-wide: changing it rewrites the harness's config file and restarts the one harness process every session shares ([harness configuration](harness-config.md)). A schedule's model instead lives on the session alone. Each fire switches its session to the schedule's model over ACP, after the session opens or resumes and before the task is prompted, so a continuous schedule picks up an edited model at its next fire. A resumed session the harness has already let go of is loaded back first: the switch waits in the runtime's prompt scheduler like a prompt would, for the harness to hold the session again but never behind a turn still running, and a load that fails or times out fails the run with its reason.

A schedule with no model runs on the **default**: the model the Agent's own Default setting gives, the harness's choice when its config file names none. It deliberately does not follow the model the Agent is set to, so switching a conversation to an expensive model never moves every routine schedule onto it. The runtime reports that default beside the Agent's model settings, without any session, and only for a harness that can switch a session's model: a model the provider pins through its environment if it pins one, otherwise the value the harness's manifest declares for selecting its built-in default in one session. Each fire switches to it unless the session already opened on it, which also returns a continuous session to the default once its model is cleared, with its history kept. A harness with no default to offer, including every harness that cannot switch a session's model, leaves a schedule without a model following the Agent's own model, as every schedule did before, and the form does not offer Default there. On a harness whose default it changed, schedules saved before the change, one-time tasks included but not one continuing its scheduling session, were migrated to the model their Agent was set to, so none changed model. An agent creating a schedule for itself can name one too.

**A schedule never silently runs on a different model.** A harness that still refuses the switch when the fire comes gets no prompt. The fire still settles, so the refusal is not redelivered, and the runtime reports it over the event report as a failed *run*, a different stage from a broken Precheck. The schedule's last result then reads as a failure with the harness's reason; a one-time task records the same failure as its result. The last-run stamp stays where it was, because nothing ran and a Precheck measures "anything new since last time?" from it. A fire that was never prompted leaves an empty session behind. Follow-up turns in a schedule's session keep its model as far as the harness restores it on reload.

## On-demand run

A schedule can also be fired from outside its recurrence: the owner asks for one run, now. Authoring a schedule is iterative — the task gets reworded, the Precheck tweaked — and with cadences hours apart, waiting for the next occurrence is as slow a feedback loop as the cadence itself.

It is deliberately *the same fire*, so what it shows is what an occurrence does: the same event kind on the same rail, carrying the same task, session mode and Precheck, decided by the Precheck as usual and reported back the same way. The runtime cannot tell the two apart, which is the point — a check that allows here allows there. What it does not do is behave like an occurrence:

- **The cadence is untouched.** No next occurrence is computed and none is armed, so trying a schedule out never shifts when it next fires — and the fire carries an identity of its own rather than an occurrence's, so the Agent's per-fire dedup cannot conflate it with the occurrence it lands beside.
- **Quiet hours do not suppress it, and neither does being disabled.** Both govern *occurrences*; this run was asked for by hand. A paused schedule is also the one most likely to be under construction, and enabling it just to try it would move its next occurrence — the thing the action exists to avoid.
- **A run that happens stamps the last-run pair** like any other, because that stamp means *the last fire that actually ran* and is what the next Precheck's "anything new since last time?" measures from — a manual run that did the work must not leave the next check to find it again. The boundary is the **outbox commit**, not the whole send: once the event is committed the task will run when the Agent is `Ready`, so any step that fails after it — the delivery enqueue or the wake poke — stamps the pair and records that failure as the result. Only a fire that never committed is not a run, and that one leaves the previous record standing.
- **Its expiry is its own.** An occurrence's fire expires at the next occurrence so a stale backlog cannot replay; an on-demand fire has no successor to be superseded by, and capping it at an occurrence minutes away would expire a run somebody is waiting for. It expires on the trigger TTL alone.

Two consequences reach what the owner reads. A **declined on-demand run counts toward the decline count** like a declined occurrence — the count is still "since the last run", but it no longer counts *occurrences* only, and leaving it uncounted would make a run the owner just asked for show nothing at all. And **usage counts an on-demand run as a fire of that schedule**, which is what it is: compute spent on that schedule's task.

The rest is inherited rather than re-decided. A hibernated Agent is poked awake and picks the fire up on its catch-up; a stopped one is started, since a fire overrides a stop by design. A continuous schedule resumes its own session, a declined verdict restores the activity stamp the poke wrote, and the session appears under the schedule's sessions like every other run. Two cases refuse outright. A one-time schedule has no cadence to try out, and a run beside its own would do the task twice. And an Agent from a [starter kit](starter-kits.md#concepts) whose onboarding is still pending: a scheduled fire is *held* there because nobody is watching; here somebody is, so the refusal is reported rather than the fire quietly vanishing.
