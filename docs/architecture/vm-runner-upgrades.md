# VM runner upgrades

Last verified: 2026-10-08

How a change to the [runner](vm-runner.md) reaches owners whose machines are running: as a **roll** of the runner pod, which reboots the owner's machines, or, for a new runner release only, as a **hand-off** inside the pod, which reboots none.

## Rolls

**A change to the runner pod rolls across owners, not all at once.** Because a pod restart reboots every machine of that owner, a new runner image or a controller release that renders the pod differently would otherwise reboot every vm machine in the install together, where container agents roll one at a time. The controller records a hash of the pod it rendered on each runner, leaves a runner alone while that hash is unchanged, and lets a changed one roll only while fewer than the install's roll width (one by default) are mid-roll. A runner is mid-roll from that moment until its new pod is ready and every machine that was ready before is ready again, or its agent is gone; a settle timeout bounds the wait for machines, so one that never comes back does not stall everyone else. A new pod that is still not ready at the timeout is a broken runner release, not a slow machine: that roll keeps its place, so the release goes no further, and is marked stalled and reported as an error until its pod becomes ready or the pod changes again. A runner whose pod is unchanged is not rolled, but labels or owner references that drifted on it are put back without touching the pod. A new owner's runner is created at once, since there is nothing of theirs to protect. Rolls advance as agents reconcile and on the periodic sweep, which offers every runner its turn in name order so owners whose agents all sleep still roll; which runners are mid-roll is read once every few seconds rather than on every turn, and a roll the controller starts counts at once. The sweep only ever updates a runner that exists — creating one is an agent's reconcile's alone. A roll still reboots each owner's machines once: nothing checkpoints them across it, and the VMM host is the same pod as the machine API it serves. So a published chart pins the runner image by digest, and a rebuild that changes nothing in the image — only the record of when and with what it was built — keeps the image it would have replaced: a release that leaves the runner as it was rolls no runner.

## Hand-offs

A [runner](vm-runner.md) pod's machines are its processes, so restarting the pod reboots every machine of its owner. Most runner changes do not need the pod restarted: what changes is the runner process, not the VMMs it started. An install that names a node directory for runner releases ([values](../../helm/values.yaml)) therefore takes a new runner image into each pod in place, without rebooting a machine. An install that names none rolls the pod for every runner image. Not supported on OpenShift yet: the directory would need an SELinux label the confined runners can read.

**A runner release** is the runner with the two guest binaries it copies into every machine's share, platform-init and platform-runc, so the side that writes a share and the side that reads it stay one version. Each release also records the **runtime** it was built against: the smolvm release with its guest agent and the libkrun the platform patches, the image tooling, and the base image's libc. The runner is itself the VMM of every machine it starts, and loads its runtime's libraries and guest agent, so the runtime travels with the release. The pod's libc does not: a release whose runner does not load in the pod can take it over only as a new pod.

**The stager** is a DaemonSet on the runners' nodes, and the only writer of the release directory. It runs the chart's runner image and copies the release that image carries under the image reference, with the runtime it names once per runtime, each appearing whole or not at all, and keeps the newest few releases and the runtimes they name. Runner pods mount the directory read-only, so a guest that escapes into its runner cannot replace a release another owner's runner takes next. A chart upgrade rolls the stager, which stages the new release.

**The loader** is the runner pod's entrypoint. It supervises one runner process and runs the release the controller names in a ConfigMap per runner, which the runner's Deployment owns. The pod's own image is always available as a release. A staged one is used once the stager has reached the pod's node, and the loader first copies it, and its runtime, into the pod: the stager may remove them from the node while a runner still copies its guest binaries from one or a VMM still serves its guest agent from the other. Before a hand-off the loader checks that the release's runner loads in the pod at all. The loader restarts a runner that exits, with a backoff, and passes a stop of the pod to the runner, which then stops every machine as the [runner](vm-runner.md) page describes.

**A hand-off** replaces the runner process. The loader signals the runner, which closes as it would for a stop but leaves every machine running, then starts the named release. The new runner reads each machine's record, finds its VMM alive, and publishes its port again, as any restarted runner does. The machines and their disks are untouched, and each keeps the runtime it booted; the machines the new runner starts boot its own runtime, so a machine moves to a new runtime at its next boot. The runner records the runtime each machine booted, and manages a machine on another runtime assuming the two are compatible, rather than testing every pair of releases: a runtime error on such a machine, or a guest quiet for half a minute instead of ten, reboots it onto the runner's own runtime. platform-init flushes the agent's home to the disk when the workload stops, so a stop whose quiesce an older guest agent does not confirm, which the runner ends with a power-off, costs a journal replay and not the agent's last writes. The loader keeps a runtime in the pod while any VMM still maps it. Connections already open through a published port drop with the old process, and the machine API is down for the seconds between the two. A VMM whose runner exited is reaped by the pod's init. A release that exits within a minute of taking over is held as **failed**, and the loader goes back to the release it replaced until the controller names another.

**What the controller does.** It writes the configured runner image into every runner's ConfigMap at once: a hand-off reboots nothing, so it is not held to the roll's width, and the loader's fallback bounds a broken release. The pod's image is left out of what the roll compares, so a runner pod rolls only for a change to its shape. The runner serves what its loader holds and why, with the reason drawn from a fixed vocabulary: not staged yet, built for another pod, or failed. The controller reads it for a runner whose pod image is not the configured one. A release built for another pod rolls the pod, onto the configured image; so does every release built against another runtime when the install keeps one runtime per pod, the switch back should a new runtime not manage machines an older one started; a release not yet staged is waited for; a failed one is never rolled onto, since a pod on it would fail the same way and take the machines with it. What the loader is given, and what the runner reports, are held in the contract documents beside the runner ([`packages/vm-runner/contract/`](../../packages/vm-runner/contract/)).
