# ADR-045: Encrypt `identity_links.refresh_token` at rest

**Date:** 2026-05-19
**Status:** Accepted
**Owner:** @jezekra1

## Context

ITSS Ch 1 §5.1 requires encryption at rest for Confidential data. `identity_links.refresh_token` (Keycloak refresh tokens for linked Slack/Telegram users — see [ADR-027](027-slack-user-impersonation.md)) is the only plaintext credential in Postgres and the only filed ITSS deviation. §5.2 (KMS-grade key management) is not required. OpenShift etcd encryption is being enabled cluster-wide.

## Decision

Column-level AES-256-GCM encryption inside the api-server. The DEK is a 32-byte random value generated by the Helm chart, persisted as a K8s Secret using the existing `lookup` pattern (see [postgres-secrets.yaml](../../deploy/helm/platform/templates/postgres-secrets.yaml)) and mounted into the api-server as an env var. Stored form: `"enc:" + base64(version(1) ‖ nonce(12) ‖ ciphertext ‖ tag(16))` in the existing `text` column. The `"enc:"` prefix discriminates ciphertext from legacy plaintext — Keycloak JWT and opaque refresh tokens never start with it. Implemented as a ~60-line `cipher.ts` helper using `node:crypto`; no third-party library.

## Alternatives Considered

- **PVC-level encryption only** — would satisfy §5.1 with zero app changes. Rejected: backups/dumps pipeline doesn't preserve the property end-to-end and operational scope was larger than expected.
- **Move `refresh_token` out of Postgres into a K8s Secret per linked user** — matches existing channel-secret pattern, zero new crypto. Rejected: column encryption was preferred over the schema change.
- **KMS-envelope encryption (IBM Cloud KMS / Vault)** — strongest §5.2 story. Rejected: §5.2 not required; pulls in cluster→KMS dependency and IAM plumbing.
- **`@47ng/cloak` (or similar library)** — established envelope, key fingerprint built in. Rejected: 50 LOC of NIST primitive composition is smaller and more auditable than a single-maintainer dep.

## Consequences

- Repo invariant: every write to `identity_links.refresh_token` must go through `cipher.encrypt`; every read through `cipher.decrypt`. Enforced by the repository being the only writer.
- The envelope's leading version byte lets us swap algorithms in the future without a data migration; bump on change.
- Losing the K8s Secret = unrecoverable refresh tokens → forced re-OAuth for every linked user. Acceptable: refresh tokens are short-lived (Keycloak default 30d) and re-link is one click.
- Existing plaintext rows are lazily re-encrypted on first read after deploy — repository detects the missing `"enc:"` prefix, encrypts in place, returns plaintext to the caller. No data migration; no forced re-OAuth.
- Rotation is not automatic. To rotate the DEK, run an explicit re-encrypt pass (read with old key, write with new key, swap the Secret) — out of scope for §5.1.
